# 图片数据集处理框架 PRD

## 项目背景

在多模态、YOLO 等模型训练前期，图片数据集的导入、处理、增强与质量控制会直接影响模型训练效率和最终效果。企业内部常见的数据来源包括本地目录、局域网文件系统、对象存储、URL 清单以及已有数据集文件，但这些来源通常分散、格式不统一、质量不可控，导致数据工程师和标注团队需要反复编写临时脚本完成扫描、清洗、过滤、整理和导出。

本项目希望建设一个图片数据集处理框架，把图片导入、基础信息提取、清洗算子编排、增强、结果输出和可视化查看沉淀为可复用能力，帮助团队稳定地产出可训练的数据集。

## 产品定位

图片数据集处理框架是面向数据工程师和标注团队的企业级图片数据处理工具，主要用于将多来源图片统一导入、清洗、增强，并输出可直接进入训练前处理流程的数据集。

该框架第一阶段重点解决“数据怎么进来、怎么形成原始数据集、怎么通过可配置清洗流程筛掉低质量数据、怎么查看处理结果、怎么输出可训练数据集”的问题。后续可以在同一套公共能力之上扩展搜索筛选、数据集版本管理和权限管理等模块。

## 第一版范围边界

第一版优先交付 Python 包能力和 Jupyter Notebook 验证链路，不实现服务端 API、Web 页面、多用户权限、跨机器分布式 DAG 调度和图片增强。

第一版清洗流程采用“Recipe 配置 + 逻辑算子列表 + 物理执行融合 + 结果归并”的方式：

1. 用户配置的是逻辑算子列表，例如格式检查、尺寸检查、模糊检测、亮度检测、重复检测。
2. 清洗平台使用 CleaningRecipe 表达一次清洗流程，包括输入数据集、输出位置、逻辑算子列表、执行配置和归并策略。
3. 逻辑算子是用户可见的细粒度能力，物理执行由 ExecutionPlanner 生成 ExecutionPlan 后交给 ExecutionPack 完成。
4. 多个逻辑算子可以共享读取、解码、特征、索引和第三方工具调用，例如多个质量算子融合到 OpenCVQualityPack，近重复、离群和聚类融合到 FastdupVisualPack。
5. 物理执行完成后，清洗平台把后端输出标准化为每个逻辑算子的 node_result、node_status_matrix 和 node_report，再通过归并策略生成 clean、dropped、full 数据集。

第一版主要验证目标是十万级图片数据集的单机处理能力。百万级图片作为架构演进目标保留，不作为第一版所有算子的生产级性能承诺。

## 目标用户与核心场景

### 目标用户

1. 数据工程师：负责收集、整理、清洗、增强和导出训练数据。
2. 标注团队：第一版主要消费导出的 clean 数据集和静态报告，不直接操作框架。
3. 算法工程师：作为下游用户，消费处理后的训练数据集。

### 核心场景

1. 数据工程师从本地目录、对象存储或已有数据集文件中导入大量图片。
2. 系统扫描图片来源，建立图片索引，提取基础信息，并生成原始数据集文件。
3. 数据工程师通过清洗平台配置数据集来源、输出位置、批处理参数、worker 参数和逻辑算子列表。
4. 系统根据处理结果输出 clean、dropped、full 三类数据集。
5. 数据工程师查看被丢弃图片、重复图片分组、异常样本和各算子处理结果。
6. 标注团队或算法工程师使用输出数据集进入标注、训练或进一步分析流程。

## 产品目标

1. 支持图片数据集从多种来源进入统一处理流程。
2. 支持在导入阶段提取图片基础信息，并形成原始数据集。
3. 支持通过统一清洗平台编排可插拔清洗算子，完成质量识别、重复识别、异常识别和内容风险识别。
4. 支持输出结构化、可追踪、可复用的数据集文件。
5. 支持查看清洗结果、丢弃原因、重复分组和数据集分布。
6. 第一版支持单服务器多核处理十万级图片，并为百万级图片处理预留架构演进空间。
7. 为后续搜索筛选、数据集版本管理和权限管理预留公共能力基础。

## 核心能力范围

### 公共基础能力

公共基础能力为各功能模块提供统一支撑，不绑定某一个具体业务流程。

1. 存储能力：支持文件系统和对象存储，候选对象存储为 MinIO。
2. 元数据能力：记录图片来源、基础属性、清洗状态、算子结果和失败原因。
3. 数据集能力：以 Parquet 为主格式，CSV、JSONL 作为辅助导出格式，承载 raw、clean、dropped、full 等数据集。
4. 任务能力：第一版支持批量处理、物理执行包融合、逻辑算子级失败记录、执行包级失败记录、批次级断点恢复和处理报告；复杂分布式 DAG 编排作为后续能力。
5. 检索能力：后续可接入 Milvus 或 Weaviate 等向量检索能力，用于语义搜索和相似图片分析。

### 功能模块

功能模块构建在公共基础能力之上，不作为线性层级关系理解。

1. 图片导入模块：负责接入不同图片来源，提取基础信息，并形成原始数据集。
2. 图片清洗平台：负责配置数据集来源、输出位置、worker、逻辑算子列表、物理执行计划、执行包调度、结果标准化和结果归并。
3. 清洗算子库：负责提供可插拔、可加载的逻辑算子规格和物理执行后端能力。
4. 图片增强模块：作为后续能力预留，第一版不实现增强处理。
5. 数据集可视化模块：用于查看数据集、筛选图片、分析清洗结果和定位异常样本。

## 功能需求

### 图片导入

图片导入模块负责把不同来源的图片接入统一处理流程，并在导入阶段完成基础信息提取，形成原始数据集。

1. 支持从本地或局域网文件系统递归扫描图片文件。
2. 支持从对象存储或 S3 类型存储中读取图片。
3. 支持从 URL 或 URL 清单中导入图片。
4. 支持从已有数据集文件导入图片清单，文件格式包括 Parquet、CSV、JSON 或 JSONL。
5. 支持把扫描到的图片存储到文件系统或对象存储。
6. 支持建立图片唯一索引，首版可采用 UUID 的方式。
7. 支持提取目录、原始文件名、后缀名、图片备注等来源元数据。
8. 支持提取图片尺寸、像素、文件大小、格式、哈希值等基础图片信息。
9. 支持生成原始数据集文件，作为后续清洗、增强和可视化查看的输入。

### 图片清洗平台

图片清洗平台负责提供统一的数据集输入、算子配置、物理执行融合和结果输出能力。清洗平台不和具体算法强绑定，具体清洗能力由可插拔算子提供。

1. 支持加载指定图片数据集，输入格式包括 Parquet、CSV、JSON 或 JSONL。
2. 支持配置数据集来源、输出位置、输出格式和处理报告位置。
3. 支持配置 worker、批处理大小和清洗执行参数。
4. 支持把一个或多个逻辑清洗算子配置为列表。
5. 支持根据逻辑算子列表生成 ExecutionPlan，并把可共享计算融合到物理 ExecutionPack。
6. 支持逻辑算子根据自身配置把后端输出解释为节点级状态和建议动作，并支持清洗平台根据归并策略生成最终过滤结果。
7. 支持输出 clean、dropped、full 三类数据集：
   - clean：通过清洗规则、可用于后续训练或标注的数据。
   - dropped：被过滤的数据，并保留过滤原因。
   - full：包含全部图片及完整清洗结果的数据。
8. 支持保留处理报告、失败图片清单、算子执行状态和可追踪原因。

### 清洗算子库

清洗算子库是解耦的、可加载的清洗算法层。清洗平台负责编排和执行算子，算子负责完成具体检测、识别或打分能力。

1. 格式类算子：
   - 损坏、截断、无法加载。
   - 空文件。
   - 格式错位。
   - 动图。
2. 尺寸类算子：
   - 超大尺寸。
   - 超小尺寸。
   - 比例异常。
3. 质量类算子：
   - 模糊。
   - 曝光异常：过曝、欠曝。
   - 噪声。
   - 马赛克。
   - 截断或内容缺失。
   - 黑白图。
4. 重复类算子：
   - 精准重复。
   - 感知哈希重复。
   - 语义重复。
5. 内容类算子：
   - 水印。
   - 信息过少。
6. 合规类算子：
   - 个人隐私。
   - 敏感内容：NSFW。

### 图片增强

图片增强模块用于提升训练数据的可用性和多样性。第一版不实现图片增强，本节仅作为后续产品方向记录。

1. 后续支持对 clean 数据集执行训练前增强处理。
2. 后续支持保留增强前后图片之间的关系。
3. 后续支持输出增强后的训练数据集。
4. 具体增强策略、参数配置和实现方式在后续架构设计或算法设计文档中定义。

### 数据集可视化

数据集可视化模块用于查看导入、清洗和增强后的数据集，帮助数据工程师确认清洗结果是否符合预期。

1. 支持查看 raw、clean、dropped、full 数据集中的图片。
2. 支持查看被丢弃图片及对应丢弃原因。
3. 支持查看重复图片分组。
4. 支持查看损坏图片、异常尺寸图片、低质量图片和敏感内容图片。
5. 支持按数据集、算子、清洗状态、丢弃原因、分数或标签筛选图片。
6. 支持查看各清洗算子的结果分布和处理统计。

### Web 页面

Web 页面首阶段不做实现，但作为后续产品形态预留。

1. 图片导入页面：用于选择来源、配置导入任务、查看导入结果。
2. 图片清洗页面：用于选择数据集、配置清洗算子列表、配置 worker、执行清洗任务、查看处理结果。
3. 数据集可视化页面：用于查看指定数据集中的图片、状态、过滤原因、重复分组和算子结果。

## 架构视角

本项目不把所有能力设计成单一线性层级，而是采用“公共基础能力 + 功能模块”的方式组织。

公共基础能力包括存储、元数据、数据集文件、运行状态、报告和检索能力。图片导入、图片清洗平台、清洗算子库、图片增强、数据集可视化、搜索筛选等模块共享这些公共能力。

图片清洗平台和清洗算子库需要保持解耦：清洗平台负责输入输出、Recipe 配置、ExecutionPlan 生成、ExecutionPack 调度、逻辑算子状态管理、结果标准化、结果归并和 worker 管理；清洗算子库负责具体逻辑算子规格、候选后端和节点级结果解释，并以可加载方式接入清洗平台。复杂分布式 DAG 编排和更强成本优化器作为后续演进能力。

候选技术包括：

1. 主要语言：Python。
2. 服务框架：FastAPI。
3. 对象存储：MinIO 或文件系统。
4. 关系数据库：PostgreSQL。
5. 向量检索：Milvus 或 Weaviate，作为后续语义搜索和相似图片能力候选。
6. 数据集格式：Parquet 为主，CSV、JSONL 为辅。
7. 图片清洗与增强工具：Pillow、OpenCV、fastdup、cleanvision、Data-Juicer、YOLO、CLIP。
8. 开发验证方式：第一版核心能力优先以 Python 包结构沉淀，可使用 Jupyter 做功能验证，后续再通过 FastAPI 包装为服务能力。

具体数据表结构、数据集 schema、算子接口、API 设计和任务调度实现不在本文档中展开，后续单独撰写架构设计文档。

## 输出产物

### 导入阶段输出

1. 原始数据集文件。
2. 导入任务报告。
3. 导入失败文件清单。

### 清洗阶段输出

1. full 数据集：包含全部图片及清洗结果。
2. clean 数据集：通过清洗规则、可用于训练或标注的数据。
3. dropped 数据集：被过滤的数据及过滤原因。
4. 清洗任务报告。
5. 失败图片清单。
6. 算子执行结果汇总。

### 增强阶段输出

增强阶段输出不属于第一版交付范围，后续版本可以输出：

1. 增强后的训练数据集。
2. 增强处理报告。
3. 原始图片与增强图片之间的关系记录。

### 第一版最小产物契约

第一版输出数据集需要遵守最小字段契约，具体字段类型和 schema version 在架构文档中定义：

1. raw 数据集至少包含 image_id、source_uri、image_uri、基础文件属性、基础图片属性和导入状态。
2. node_result 保存逻辑算子的原始结果或工具输出。
3. node_status_matrix 保存逻辑算子对每张图片的节点级状态、建议动作、原因、分数和错误信息。
4. clean、dropped、full 由归并策略生成，必须保留 image_id、image_uri、最终状态和可追踪原因。
5. 对外共享或训练导出默认使用 image_uri；如需隐藏真实存储位置，应通过导出配置复制图片并改写导出版地址。

## 非目标与暂不展开内容

以下内容不是本文档的重点，暂不展开：

1. 不拆解开发任务优先级。
2. 不定义数据库表结构。
3. 不定义 API 协议。
4. 不实现图片爬虫。
5. 不实现 Web 页面。
6. 不实现标注协同工作流。
7. 不实现多用户权限管理。
8. 不实现图片增强。
9. 不实现跨机器分布式 DAG 调度和复杂成本优化器。
10. 不承诺所有算子达到百万级生产性能。

第一版虽然不实现多用户权限管理，但必须遵守最小安全边界：

1. 默认运行在单租户、单项目、受控目录或受控存储桶中。
2. 输出目录和对象存储桶默认私有。
3. URL 导入必须具备协议白名单、内网地址限制、下载大小限制和内容类型校验。
4. 对外导出默认不包含 source_uri，除非用户显式开启。
5. 静态 HTML 报告和缩略图默认只导出抽样结果，敏感样本默认不分享。

## 验收标准

1. 能导入一批本地图片，提取基础图片信息，并生成符合最小字段契约的 raw Parquet。
2. 能从已有 Parquet、CSV、JSON 或 JSONL 数据集文件中加载图片清单。
3. 能配置逻辑算子列表、输出位置、worker、batch_size 和执行参数，并生成 ExecutionPlan。
4. 能把至少两个共享图片解码或质量指标的逻辑算子融合到同一个 ExecutionPack，并为每个逻辑算子输出独立 node_result 和 node_status_matrix。
5. 能通过可插拔清洗算子识别损坏、异常尺寸、基础低质量图片和基础重复图片。
6. 能输出 clean、dropped、full 三类数据集，并满足 clean 行数 + dropped 行数 = full 行数。
7. 能查看被丢弃图片、丢弃原因、重复图片分组和各逻辑算子处理结果。
8. 输出数据集可直接进入训练前处理、标注或进一步分析流程，并保留 image_id、image_uri 和可追踪原因。
9. 清洗过程能保留失败清单、处理报告、算子执行状态和可追踪原因。
10. 断点恢复后，同一输入、同一配置和同一归并策略生成的数据集 fingerprint 应与一次性运行结果一致。
11. 在单服务器多核环境下，第一版需要通过十万级图片的规模验证，并记录吞吐、峰值内存、失败率和恢复耗时。

1. MinIO：对象存储，不称为对象型数据库。
2. PostgreSQL：关系数据库。
3. Milvus / Weaviate：向量检索或语义搜索能力候选。
4. Parquet：主要数据集文件格式。
5. JSONL：辅助数据集文件格式。
6. clean：通过清洗规则的数据集。
7. dropped：被过滤的数据集。
8. full：包含全部数据和处理结果的数据集。
