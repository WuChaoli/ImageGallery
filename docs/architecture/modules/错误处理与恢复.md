# 错误处理与恢复架构

本文档从总架构文档中拆分而来，承接对应功能域的详细架构设计。总架构文档只保留总体把控、模块边界和跨模块约束。

## 模块定位

错误处理与恢复模块定义导入、清洗、存储等流程中的错误分类、状态存储、断点恢复和原子提交约定。

## 职责范围

1. 定义错误分类、失败策略、失败清单和错误摘要。
2. 使用 SQLite 作为控制面 Run State Store，记录 run、operator、pack、batch 或 stage 状态。
3. 通过 artifact manifest 和原子提交保证状态与产物一致。
4. 定义 resume、overwrite、rerun、retry_failed 的恢复语义。

## 核心对象

1. Run State Store
2. SQLiteStateStore
3. ArtifactRegistry
4. failure_manifest
5. cleaning_run
6. operator_run
7. pack_run
8. batch_run
9. stage_run

## 核心流程

执行开始写入状态 -> batch/stage 更新状态和产物 -> manifest 提交 -> SQLite 标记完成 -> resume 时校验状态、manifest 和配置快照。

## 数据 / 状态 / 配置契约

1. 恢复配置归属本模块，包括 fail_fast、resume、overwrite、retry_failed、state_store_uri、run_id。
2. 清洗任务 resume=True 必须校验 config_hash、input_dataset_fingerprint、logical_operators、execution_plan、backend_config 和产物状态。
3. SQLite 只存控制面状态，不存图片级明细、状态矩阵明细、图片文件或缩略图二进制。

## 与其他模块边界

1. 各领域模块负责自己的执行入口，错误处理模块负责状态、manifest 和恢复契约。
2. 清洗平台提供 CleaningRecipe、ExecutionPlan、逻辑算子配置和后端配置快照，错误处理模块使用它判断历史状态兼容性。
3. 存储系统负责实际文件读写，错误处理模块负责 manifest 校验和提交语义。

## V1 范围与非目标

1. V1 必须支持 batch 级断点恢复和 artifact manifest 校验。
2. V1 不实现分布式事务和跨进程复杂调度锁。

## 详细设计

### 17. 错误处理与可恢复性

#### 17.1 模块定位

错误处理与可恢复性负责保证导入任务、清洗任务和导出任务在大规模图片集场景下具备可追踪、可查看、可重试和可断点恢复的能力。

第一版错误处理遵循以下分工：

1. 图片文件存储在 Storage 中。
2. Dataset、逻辑算子结果、逻辑算子状态矩阵和物理执行包 artifact 存储在 Parquet 文件或对象存储中。
3. Run、Operator、Pack、Batch 和 Stage 的运行状态存储在 SQLite 中。

也就是说，SQLite 只作为轻量级 Run State Store，不作为图片级数据集元数据库。

#### 17.2 错误分类

第一版错误可以分为两类：

1. 数据问题：单张图片损坏、图片读取失败、元数据缺失、某个样本处理失败等。
2. 系统问题：配置错误、存储不可用、输出目录不可写、依赖库不可用、算子实现异常等。

默认策略：

1. 数据问题尽量不中断整批任务，应记录到失败清单、节点状态矩阵或节点报告中。
2. 系统问题可以中断当前任务，避免继续产生不可用结果。

#### 17.3 导入阶段错误处理

图片导入阶段遇到单张图片失败时，不应中断整批导入任务。

导入任务应输出：

1. 成功导入后生成的 Dataset。
2. 导入失败清单。
3. 导入报告。

导入失败清单建议记录：

```text
source_uri
source_type
error_stage
error_code
error_message
retryable
occurred_at
```

失败样本默认不进入 raw Dataset，但必须保留可追踪原因，便于后续重试或人工排查。

#### 17.4 清洗错误处理

清洗任务处理单张图片、单个 batch 或单个 stage 失败时，默认不直接终止整个清洗 run，而是写入对应 LogicalOperator 的独立状态矩阵，并在相关 ExecutionPack 报告中记录后端错误。

逻辑算子状态矩阵可以记录：

```text
image_id
status
error_code
error_message
batch_id
processed_at
```

其中 status 可以包含：

```text
passed
flagged
failed
skipped
```

逻辑算子级错误统计写入 operator_report，物理执行包错误统计写入 pack_report，清洗任务级错误统计写入 cleaning_report，便于用户查看该算子、该后端执行包或本次清洗的成功数量、失败数量、跳过数量和错误分布。

#### 17.5 失败策略配置

CleaningContext 可以提供基础失败策略：

```text
fail_fast
max_error_ratio
max_error_count
```

默认建议：

1. fail_fast 默认为 false。
2. 单张图片或少量 batch 失败不终止任务。
3. 当错误数量或错误比例超过阈值时，当前 LogicalOperator 或 ExecutionPack 可以进入 failed 或 partial 状态。
4. 配置错误、存储不可用等系统性错误可以直接中断任务。

#### 17.6 Run State Store

为了支持断点运行，各领域流程需要持久化轻量运行状态。第一版采用轻量级 SQLite 作为 Run State Store。

Run State Store 负责记录：

1. Run 运行状态。
2. Operator 运行状态。
3. Pack 运行状态。
4. Batch 运行状态。
5. Stage 运行状态。
6. 运行事件。
7. 产物引用。
8. 错误摘要。

Run State Store 不负责存储：

1. 图片文件。
2. 图片级元数据明细。
3. 图片级清洗结果明细。
4. 图片级状态矩阵明细。
5. 缩略图。

这些大体量数据仍然存储在 Storage、Parquet 或普通文件中。

#### 17.7 SQLite 存储边界

第一版推荐每个 run 使用一个独立 SQLite 文件，和该次运行的产物目录绑定。

示例目录：

```text
work_dir/
  runs/
    run_20260701_001/
      run_state.sqlite
      artifacts/
        operator_results/
        operator_status_matrices/
        pack_artifacts/
        reports/
        tmp/
```

这种方式便于移动、归档和删除单次运行结果，也能避免全局 SQLite 文件持续膨胀。

SQLite 中可以保存以下轻量状态：

```text
cleaning_run
operator_run
pack_run
batch_run
stage_run
run_event
artifact
error_summary
```

SQLite 的统一定位是控制面存储，用于保存小而常查、需要事务、需要恢复的运行控制信息。它不替代 Storage 和 Parquet。

各模块使用 SQLite 的建议边界如下。

##### 通用运行状态

Run State Store 可以记录 run_event、artifact、batch_run、stage_run 和 error_summary。清洗平台可以在同一个状态存储中记录 cleaning_run、operator_run、pack_run、batch_run、stage_run、run_event、artifact 和 error_summary。

这些信息用于断点恢复、运行跳过、逻辑算子跳过、物理执行包跳过、重跑、失败 batch 查询和运行进度查看。

##### 图片导入模块

图片导入模块可以记录 import_run、import_progress、import_artifact 和 import_failed_summary。

这些信息用于导入任务续跑、导入进度查看、失败样本重试和 raw Dataset 产物追踪。

导入失败明细仍应输出为失败清单文件，图片级基础元数据仍应写入 raw Parquet。

##### 存储系统接入模块

存储系统接入模块可以在需要时记录已注册的具名存储库信息，例如 storage_name、storage_type、enabled 和非敏感连接摘要。

第一版也可以只通过 Python dict 或 YAML 配置注册存储库。即使后续把存储库注册信息写入 SQLite，也不应存储 MinIO secret key、访问 token 或大规模对象列表。

##### Artifact Registry

Artifact Registry 适合使用 SQLite 维护轻量产物索引。

可记录的产物包括：

1. raw Dataset。
2. pack_artifact。
3. node_result。
4. node_status_matrix。
5. operator_report。
6. pack_report。
7. merge_result。
8. clean、dropped、full 等导出 Dataset。
9. HTML report。
10. thumbnail directory。

Artifact Registry 只记录产物位置、类型、格式、行数摘要和创建时间，不保存产物内容。

##### 配置快照

SQLite 可以保存 recipe_config、logical_operator_config、execution_plan、backend_config、runtime_config 的快照和 hash，用于判断是否允许 resume。

配置快照中不应保存密钥和敏感 token。

##### 报告摘要

完整报告继续以 JSON 或 HTML 文件保存。SQLite 可以保存报告摘要和报告产物索引，例如 report_uri、total_count、failed_count、warning_count 和 duration_ms。

##### 可视化缓存索引

可视化模块可以使用 SQLite 记录缩略图缓存索引，例如 image_id、image_uri、thumbnail_uri、thumbnail_size 和 generated_at。

缩略图文件本体仍存储在文件系统或对象存储中，不写入 SQLite。

#### 17.8 不进入 SQLite 的内容

以下内容第一版不写入 SQLite：

1. 图片文件。
2. 缩略图二进制。
3. 图片级基础元数据明细。
4. 图片级清洗结果明细。
5. 图片级状态矩阵明细。
6. duplicate group 的大规模明细。
7. 大规模 Dataset 内容。
8. MinIO secret key、访问 token 等敏感凭据。

推荐分工：

```text
Storage:
  图片文件、缩略图文件、报告文件、Parquet 文件

Parquet:
  raw Dataset
  pack_artifact
  node_result
  node_status_matrix
  merge_result
  clean / dropped / full 输出数据集

SQLite:
  run 状态
  operator / pack / batch / stage 状态
  artifact 索引
  配置快照
  报告摘要
  导入进度摘要
  可选缩略图缓存索引
```

#### 17.9 Run 级状态

Run 级状态用于记录一次任务运行的整体状态。

典型字段：

```text
run_id
graph_id
status
current_operator_id
current_pack_id
started_at
updated_at
finished_at
```

Run 级状态需要回答：

1. 当前任务是否完成。
2. 当前运行到哪个逻辑算子或物理执行包。
3. 哪些逻辑算子或物理执行包已经完成。
4. 哪些逻辑算子或物理执行包失败或部分完成。
5. 当前 run 是否允许 resume。

#### 17.10 Operator 与 Pack 级状态

Operator 级状态用于记录单个逻辑算子的标准化结果状态和产物引用。Pack 级状态用于记录物理执行包的执行状态和共享 artifact 引用。

Operator 典型字段：

```text
run_id
operator_id
operator_type
status
config_hash
input_dataset_fingerprint
output_result_uri
output_status_matrix_uri
started_at
updated_at
finished_at
```

Pack 典型字段：

```text
run_id
pack_id
pack_type
backend_name
backend_version
status
config_hash
input_dataset_fingerprint
output_artifact_uri
started_at
updated_at
finished_at
```

Operator 和 Pack 级状态需要回答：

1. 逻辑算子或物理执行包是否已经完整完成。
2. 它基于哪个输入 Dataset、后端版本和配置运行。
3. 使用的配置是否和当前配置一致。
4. 逻辑算子结果、状态矩阵或 Pack artifact 写在哪里。
5. 它是否可以跳过、恢复或重跑。

#### 17.11 Batch 与 Stage 状态

对于支持 batch 的 ExecutionPack，Run State Store 记录 batch 级状态。

典型字段：

```text
run_id
pack_id
batch_id
status
input_start
input_end
result_part_uri
status_part_uri
record_count
error_count
started_at
updated_at
finished_at
```

恢复时可以跳过 completed batch，重跑 failed batch，继续处理 pending batch。

对于不适合按 batch 完成最终结果的 ExecutionPack，例如 FastdupVisualPack 或 CustomEmbeddingPack，可以使用 stage 级 checkpoint。

示例 stage：

```text
extract_features
build_index
find_groups
write_result
```

第一版可以先实现 batch checkpoint，复杂全局执行包至少应记录 stage 状态；如果某个 ExecutionPack 声明不支持 checkpoint，则恢复时需要整体重跑该 Pack。

#### 17.12 断点恢复流程

调用断点恢复时：

```text
cleaning.run(resume=True)
```

清洗平台应执行以下检查：

1. 打开当前 run 的 run_state.sqlite。
2. 检查 cleaning_run 状态。
3. 检查当前 CleaningRecipe 配置快照的 config_hash。
4. 检查 input_dataset_fingerprint。
5. 检查 logical_operators、ExecutionPlan 和 backend_config 与历史状态是否兼容。
6. 跳过已完成 ExecutionPack、LogicalOperator 标准化结果或 batch。
7. 对未完成 ExecutionPack 或 LogicalOperator 标准化步骤继续执行。
8. 对已完成 batch 跳过，对失败或未完成 batch 重跑。
9. ExecutionPack 或 LogicalOperator 完成后更新产物引用。
10. 清洗任务完成后更新 cleaning_run 状态。

如果当前配置、输入 Dataset、逻辑算子列表、执行计划或关键后端配置与历史运行状态不一致，默认拒绝 resume，要求用户显式 overwrite 或新建 run。

#### 17.13 原子提交

为避免断点状态与实际产物不一致，ExecutionPack、LogicalOperator 标准化结果和 batch 的结果写入需要遵循原子提交约定。

推荐流程：

```text
写入临时文件
  -> 校验写入结果
  -> 写入 artifact manifest
  -> 提交为正式分片
  -> 更新 SQLite 状态为 completed
```

只有产物提交成功、manifest 校验通过且状态更新成功，才认为 batch、ExecutionPack 或 LogicalOperator 标准化结果完成。

如果任务中断时发现临时文件存在但状态未完成，恢复时应优先按状态判断，未完成产物可以清理或覆盖。

对象存储和分片 Parquet 不应依赖 rename 原子性。每个正式 artifact 目录需要写入 manifest，建议包含：

```text
artifact_id
artifact_type
schema_hash
part_files
row_count
checksum
created_at
commit_marker
```

恢复时需要同时校验 SQLite 状态和 artifact manifest。SQLite 显示 completed 但 manifest 缺失或 part 缺失时，应把该产物视为不可用并要求重跑对应 batch、ExecutionPack 或 LogicalOperator 标准化步骤。

#### 17.14 重试与重跑

第一版可以支持以下恢复入口：

```text
cleaning.run(resume=True)
cleaning.run(overwrite=True)
cleaning.rerun_operator(operator_id, overwrite=True)
cleaning.rerun_pack(pack_id, overwrite=True)
cleaning.resume_pack(pack_id)
image_import.retry_failed()
```

语义约定：

1. resume=True：校验配置快照、输入指纹、逻辑算子列表、执行计划、后端配置和产物状态，跳过已完成 Pack、逻辑算子结果或 batch，继续未完成部分。
2. overwrite=True：清理旧结果，重新运行。
3. rerun_operator：重新生成指定逻辑算子的标准化结果，并按需触发相关 Pack。
4. rerun_pack：重新运行指定物理执行包。
5. resume_pack：恢复指定执行包未完成 batch 或 stage。
6. retry_failed：基于导入失败清单重试失败样本。

#### 17.15 临时文件管理

任务运行过程中的临时文件应写入 run 目录下的 tmp 子目录。

示例：

```text
work_dir/runs/{run_id}/artifacts/tmp/
```

原则：

1. 正式产物和临时产物目录分离。
2. batch 成功后再提交正式分片。
3. 任务失败时默认保留临时目录，方便排查。
4. 提供 cleanup_tmp 能力清理临时文件。

#### 17.16 报告体系

每个任务和节点都应生成轻量报告。

报告类型：

1. import_report。
2. graph_report。
3. node_report。

报告记录摘要，不记录大规模图片级明细。

报告内容可以包括：

1. 输入数量。
2. 成功数量。
3. 失败数量。
4. 跳过数量。
5. 输出产物路径。
6. 错误分布。
7. 开始时间、结束时间和耗时。
8. 配置摘要。

#### 17.17 设计原则

1. 数据问题尽量不中断任务，系统问题及时中断。
2. 所有失败都必须可查看、可解释、可重试。
3. SQLite 只存运行状态，不存图片级数据明细。
4. Parquet 存数据，SQLite 存运行状态，图片存 Storage。
5. Import、Cleaning、Operator、Pack、Batch 和 Stage 都应有可追踪状态。
6. 断点恢复必须校验配置、输入 Dataset 和算子类型。
7. 节点结果写入应遵守原子提交约定。
