# 存储系统架构

本文档从总架构文档中拆分而来，承接对应功能域的详细架构设计。总架构文档只保留总体把控、模块边界和跨模块约束。

## 模块定位

存储系统为图片、数据集文件、报告、临时文件和产物 manifest 提供后端存储库接入、对象读写和受管路径能力。

## 职责范围

1. 管理用户命名的后端存储库，第一版支持本地文件系统和 MinIO。
2. 采用单个 Storage 实例连接单个后端库的方式，上层调用可通过库名称选择写入位置。
3. 为导入、清洗、可视化和报告提供统一读写能力。
4. 约束受管输出路径，避免算子和任务绕过平台写出。

## 核心对象

1. Storage
2. FileSystemStorage
3. MinioStorage
4. image URI resolver
5. managed output path

## 核心流程

调用方创建特化 Storage 实例 -> 通过具体后端的显式 `connect(...)` 参数建立并校验连接 -> 调用 Storage 实例方法执行读写 -> 返回 image_uri 或产物 URI。

## 数据 / 状态 / 配置契约

1. storage_config 归属本模块，包括 default_storage、storages、storage type、root、endpoint、bucket 等。
2. 图片级数据集统一保存 image_uri，image_uri 必须是当前环境可直接访问的绝对地址。
3. 对外导出默认保留 image_uri，但敏感 source_uri 默认不导出。

## 与其他模块边界

1. 存储系统不理解 Dataset、导入任务和清洗任务的业务语义。
2. Dataset、importers、cleaning、visualization 都通过 Storage 抽象访问存储，不直接依赖具体 SDK。
3. artifact manifest 的校验语义由错误处理与恢复模块定义。

## V1 范围与非目标

1. V1 支持本地文件系统和 MinIO。
2. V1 不支持复杂权限系统、跨区域复制和多租户存储治理。

## 详细设计

### 12. 存储系统接入设计

#### 12.1 模块定位

存储系统接入层是公共基础能力之一，负责屏蔽不同后端存储库的差异，为图片导入、清洗、增强、可视化和导出提供统一的存储访问能力。

第一版支持两类后端存储库：

1. 文件系统存储库。
2. MinIO 对象存储库。

#### 12.2 具名后端存储库

平台接入的后端存储库必须具名。存储库名称用于区分不同后端存储实例，上层调用存储能力时可以显式指定使用哪个库。

需要区分两个概念：

1. storage_type：存储类型，例如 filesystem、minio。
2. storage_name：用户命名的单个后端存储库实例，例如 local_main、minio_prod、minio_training。

每个 Storage 实例只连接一个后端库。多个 storage_name 可以使用同一种 storage_type。例如，minio_prod 和 minio_training 都可以是 MinIO 类型，但代表不同的后端存储库实例。

#### 12.3 image_uri 图片地址

第一版以 Python package 和 Jupyter 调试形态为主，不要求存在长期运行的平台进程或全局配置中心。因此图片级数据集不使用平台统一地址作为主引用，而是统一使用 image_uri 字段保存绝对地址。

本地文件系统存储推荐使用绝对路径或 file URI：

```text
/data/image_gallery/project_a/storage/images/raw/0001.jpg
file:///data/image_gallery/project_a/storage/images/raw/0001.jpg
```

MinIO 或其他对象存储可以使用当前环境可访问的对象地址或显式生成的访问地址：

```text
s3://bucket/images/raw/20260701/import_001/0001.jpg
https://minio.example.com/bucket/images/raw/20260701/import_001/0001.jpg
```

image_uri 是后续清洗、可视化和导出的图片主引用。它必须能在当前运行环境中直接读取，避免调用方重新打开 Dataset 时还需要依赖某个外部 platform URI 解析配置。

#### 12.4 地址解析器

地址解析器负责把 Storage 写入返回值、用户输入路径和后端对象地址规范化为 image_uri。

必须支持：

1. object_path + storage_name -> image_uri：用于 Storage 写入后返回图片主引用。
2. image_uri -> 存储访问句柄：用于平台内部读取对象。
3. 本地相对路径 -> 绝对路径或 file URI：仅在调用方显式传入 base_dir 时支持。

可以支持：

1. image_uri -> storage_name + object_path：仅当地址能明确识别为已注册存储库中的对象时支持。

地址解析器的基本过程：

```text
/data/image_gallery/project_a/storage/images/raw/0001.jpg
  -> 识别为本地文件绝对路径
  -> 直接读取或交给 FileSystemStorage

storage = MinioStorage(storage_name="minio_prod")
  -> storage.connect(endpoint="127.0.0.1:9000", access_key="...", secret_key="...", bucket="images", secure=False)
  -> storage.write_bytes("images/raw/0001.jpg", data) 写入对象并返回 image_uri
```

#### 12.5 Storage 抽象类

Storage 抽象类表示一个已经连接到单个后端库的存储库实例。图片导入模块、清洗模块、增强模块和可视化模块都应依赖 Storage 抽象，而不是直接依赖 MinIO SDK 或文件系统细节。

第一版需要一个抽象基类和两个具象实现：

1. Storage：抽象基类，定义统一对象操作接口和默认批量操作。
2. FileSystemStorage：面向本地或挂载文件系统。
3. MinioStorage：面向 MinIO 对象存储。

Storage 需要提供统一能力：

1. connect：建立或校验到后端库的连接，连接后返回可操作的 Storage 实例。
2. write_bytes：写入对象并返回 image_uri。
3. read_bytes：读取对象内容。
4. exists：判断对象是否存在。
5. delete：删除对象。
6. copy：复制对象。
7. move：移动对象。
8. make_image_uri：根据 object_path 生成 image_uri。
9. write_many、read_many、exists_many、delete_many：批量操作，第一版可由抽象基类基于单对象方法循环实现。

推荐接口形态：

```text
FileSystemStorage.connect(root) -> FileSystemStorage
MinioStorage.connect(endpoint, access_key, secret_key, bucket, secure=False) -> MinioStorage
Storage.write_bytes(object_path, data, overwrite=False) -> image_uri
Storage.read_bytes(object_path) -> bytes
Storage.exists(object_path) -> bool
Storage.delete(object_path) -> None
Storage.copy(src_object_path, dst_object_path, overwrite=False) -> image_uri
Storage.move(src_object_path, dst_object_path, overwrite=False) -> image_uri
Storage.make_image_uri(object_path) -> image_uri
```

批量操作需要返回逐项结果。单个对象失败不应中断整批操作，调用方可以根据逐项状态生成导入失败清单或重试任务。

#### 12.5.1 特化 Storage 连接入口

第一版不使用统一注册入口。调用方直接创建具体 Storage 类，并在 `connect` 中传入连接地址、凭证或本地 root；`connect` 必须完成连接检查并返回活跃可用的 Storage 实例。

推荐调用方式：

```text
storage = FileSystemStorage(storage_name="local_main").connect(root="/data/image_gallery/storage")
image_uri = storage.write_bytes("images/raw/0001.jpg", data)

minio_storage = MinioStorage(storage_name="minio_prod").connect(
    endpoint="127.0.0.1:9000",
    access_key="admin",
    secret_key="YourStrongPassword123",
    bucket="images",
    secure=False,
)
```

连接参数缺失、目录不可读写、bucket 不存在或服务不可达时，都必须抛出 Storage 模块自己的明确错误。

#### 12.6 数据集中的地址写入原则

平台内部 raw、clean、dropped、full 等图片级数据集默认写入 image_uri。

image_uri 是当前版本唯一的图片主地址字段，不再额外保存 storage_path 或 resolved_uri 两套字段。这样可以保证 Dataset 被单独交给 Notebook、训练脚本或临时分析脚本时，仍然能直接定位图片。

推荐原则：

1. 图片主引用统一使用 image_uri。
2. image_uri 保存当前环境可访问的绝对地址。
3. 原始追溯保留 source_uri。
4. source_uri 是审计字段，对外共享和训练导出默认移除。
5. 如后续平台化需要跨环境迁移，可另行增加 manifest 或平台地址字段，不影响 V1 的 image_uri 主字段。

#### 12.6.1 受管输出路径

第一版虽然允许调用方提供 output_path 或 output_dir，但存储层必须做受管路径校验：

1. output_path 必须属于已注册 storage_name 对应的后端库，或属于明确允许的本地根目录。
2. object_path 需要规范化，拒绝 `..`、符号链接逃逸和跨 storage 写入。
3. 默认禁止覆盖已有正式产物，除非调用方显式设置 overwrite。
4. 临时产物必须写入 run 目录下的 tmp 子目录，正式产物必须通过原子提交或 manifest 提交。
5. 静态报告、缩略图和导出数据集默认写入受管输出目录，避免落入共享目录或不可追踪路径。

#### 12.7 存储接入边界

存储系统接入层负责：

1. 管理具名后端存储库。
2. 屏蔽文件系统和 MinIO 的访问差异。
3. 根据 storage_name 和 object_path 写入对象。
4. 生成 image_uri。
5. 校验 image_uri 和受管输出路径。

存储系统接入层不负责：

1. 扫描外部数据源。
2. 判断图片是否应该进入 clean 或 dropped 数据集。
3. 生成 raw、clean、dropped、full 数据集。
4. 执行清洗算子。
