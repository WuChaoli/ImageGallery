# 清洗平台与算子库架构 v3

本文档是清洗平台与算子库的 v3 设计草案，用于承载从 v2 到自研算子框架的破坏式调整。v3 的核心目标是把清洗过程拆成“参数计算”和“逻辑评估”两层，同时让多个计算单元共享图片读取、解码和批处理上下文。

v3 完全移除 fastdup 依赖、fastdup adapter 和 fastdup 风格的执行假设。近重复、聚类、离群等能力后续由自研参数计算单元、relation table 和 artifact 产物逐步承载。

## 模块定位

清洗平台负责基于 raw Dataset 执行一组逻辑算子，生成可复用的图片参数表、关系类产物和逻辑评估表，并支持用户在 Notebook 或 Python API 中查看、调整、预览和导出结果。

v3 不再把底层工具后端作为执行组织中心，而是以参数生产为中心：

```text
Dataset
  -> Cleaner([{operator_name: config}, ...])
  -> collect required parameters
  -> compute parameter_table / relation artifacts
  -> evaluate logical operators
  -> evaluation_table
  -> preview() / state() / export()
```

用户仍然只感知逻辑算子，例如 `quality.blur_check`、`duplicate.exact_duplicate_check`、`content.blank_image_check`。平台内部先根据这些逻辑算子收集参数需求，再统一组织参数计算。

## 核心原则

1. 逻辑算子是用户侧稳定能力单元，不是底层图片读取和批量计算单元。
2. 逻辑算子承载清洗语义、参数需求声明、默认配置、评估规则和评估输出列。
3. `ParameterComputer` 承载批量 IO、解码复用、参数生产、关系产物和 artifact 生成。
4. 同一个 `ParameterComputer` 可以服务多个逻辑算子。
5. Cleaner 根据已启用逻辑算子合并参数需求，先计算参数，再批量评估。
6. 多个图片级 `ParameterComputer` 默认按 batch 共享图片读取和解码结果。
7. 数据集级 `ParameterComputer` 在图片级参数就绪后运行，用于重复组、聚类、近邻和离群等全局能力。
8. `parameter_table` 只保存图片级单值参数、摘要字段和 artifact 引用。
9. pair、group、graph、index、embedding 等复杂结果使用 relation table 或 artifact。
10. `evaluation_table` 只保存逻辑算子的判断结果、action、reason、score 和最终归并列。
11. raw Dataset 在清洗过程中保持不可变，clean、dropped、review、full 都是基于评估表导出的视图。
12. 第一版不引入通用 DAG、重型 Planner 或跨 run 缓存系统。

## 核心对象

v3 清洗平台保留少量核心对象：

1. `Cleaner`：用户侧主要入口，定义 `run`、`preview`、`state`、`config`、`rerun`、`result`、`export`。
2. `BasicCleaner`：第一版基础清洗策略，负责解析逻辑算子、合并参数需求、执行参数计算、执行评估和导出视图。
3. `LogicalOperatorSpec`：逻辑算子规格，声明算子名称、参数需求、默认配置、评估函数和评估输出列。
4. `OperatorRegistry`：维护 `operator_name` 到 `LogicalOperatorSpec` 的映射。
5. `ParameterSpec`：参数字段规格，描述字段名、字段类型、生产者、计算配置哈希和是否可复用。
6. `ParameterComputer`：参数计算单元，按批次或全局表生产参数列、relation table 或 artifact。
7. `ComputePlan`：Cleaner 内部临时计划，记录本次 run 需要哪些参数、哪些 computer、哪些阶段。
8. `CleanerRunState`：记录 run_id、输入 dataset 指纹、启用算子、配置快照、输出表路径和运行摘要。

`ComputePlan` 只是 Cleaner 运行期的轻量结构，不升级为用户可见的通用执行图。

## 逻辑算子职责

逻辑算子负责表达“要检查什么”，而不是“如何批量读取和计算图片”。

单个逻辑算子负责：

1. 声明稳定名称，例如 `quality.blur_check`。
2. 声明需要的参数字段，例如 `blur_score`。
3. 声明评估输出列，例如 `blur_score`、`blur_action`、`blur_reason`。
4. 定义默认评估配置，例如阈值、动作和 reason 规则。
5. 基于 `parameter_table`、relation 摘要或 artifact 引用生成评估列。

逻辑算子不负责：

1. 自己读取图片。
2. 自己做批处理调度。
3. 自己复用解码缓存。
4. 自己写 `parameter_table`。
5. 自己生成全局 final action。
6. 自己维护跨算子执行顺序。

示例：

```text
quality.blur_check
  required_parameters:
    - blur_score
  evaluation_outputs:
    - blur_score
    - blur_action
    - blur_reason
  evaluator:
    blur_score < threshold -> action

quality.brightness_check
  required_parameters:
    - brightness_score
  evaluation_outputs:
    - brightness_score
    - brightness_action
    - brightness_reason
  evaluator:
    brightness_score outside min/max -> action
```

这样新增逻辑算子时，优先复用已有参数。如果新逻辑只需要已有参数，只新增 evaluator；只有确实缺少参数时，才扩展或新增 `ParameterComputer`。

## ParameterComputer 职责

`ParameterComputer` 负责表达“如何高效生产参数”。

单个 `ParameterComputer` 负责：

1. 声明可生产的参数列。
2. 声明运行阶段，例如 image batch、table derived、dataset global。
3. 接收本次实际需要的参数列，只计算被请求的列。
4. 在 batch 内共享已读取和已解码的图片对象。
5. 写回 `parameter_table` 更新列、relation table 或 artifact 引用。
6. 记录参数生产所依赖的计算配置，用于后续判断是否可复用。

`ParameterComputer` 不负责：

1. 产生 `action` 或 `reason`。
2. 理解某个清洗策略是否应该 drop 或 review。
3. 管理用户传入的逻辑算子配置。
4. 修改 raw Dataset 或图片资产。

示例：

```text
image_metadata_computer
  stage: image_batch
  outputs:
    - width
    - height
    - format
    - decode_ok
    - decode_error

image_quality_computer
  stage: image_batch
  inputs:
    - decoded_image
    - grayscale_image
  outputs:
    - blur_score
    - brightness_score
    - contrast_score

image_hash_computer
  stage: image_batch
  inputs:
    - decoded_image
    - raw_bytes
  outputs:
    - content_hash
    - phash

duplicate_group_computer
  stage: dataset_global
  inputs:
    - content_hash
    - phash
  outputs:
    - exact_duplicate_group_id
    - near_duplicate_group_id
    - nearest_neighbor_id
    - nearest_neighbor_score
  relation_outputs:
    - duplicate_pairs.parquet
```

## 执行阶段

v3 默认使用三阶段执行。

### 阶段 1：图片批次参数计算

图片级参数计算按 batch 执行。Cleaner 先读取一批图片，再把共享的图片上下文传给多个 `ParameterComputer`。

```text
for batch in dataset:
  image_batch = read_and_decode_once(batch)
  image_metadata_computer.compute(image_batch)
  image_quality_computer.compute(image_batch)
  image_hash_computer.compute(image_batch)
  append parameter updates
```

这个阶段适合生产：

```text
width
height
format
decode_ok
decode_error
file_size
blur_score
brightness_score
contrast_score
content_hash
phash
```

默认不要求多个 computer 对同一张图并行执行。第一版优先保证同一 batch 内共享读取和解码结果；后续如果需要提升吞吐，可以在 batch 级并发、computer 内部并发或 worker pool 上扩展。

### 阶段 2：表级和数据集级参数计算

当图片级参数就绪后，平台执行不需要再次读取原图的派生计算和需要全局上下文的计算。

表级派生适合：

```text
aspect_ratio
megapixels
size_bucket
quality_bucket
```

数据集级计算适合：

```text
exact_duplicate_group_id
near_duplicate_group_id
nearest_neighbor_id
nearest_neighbor_score
cluster_id
outlier_score
relation_artifact_ref
```

数据集级 computer 可以读取 `parameter_table`、relation table 或 artifact，但不应重新逐算子扫描图片。确实需要图片特征时，应优先依赖阶段 1 已产出的参数或 artifact。

### 阶段 3：逻辑算子评估

所有必要参数就绪后，Cleaner 对已启用逻辑算子逐个执行 evaluator。

```text
for operator in enabled_operators:
  updates = operator.evaluate(parameter_table, config)
  update evaluation_table

evaluation_table = apply_final_action(evaluation_table)
```

评估阶段不读取图片，不调用 `ParameterComputer`，不修改 `parameter_table`。阈值、action 或 reason 规则变化时，优先只重算评估列。

## 参数需求合并

Cleaner 运行时从所有启用逻辑算子收集参数需求。

示例：

```text
enabled operators:
  format.decode_check
  size.dimension_check
  quality.blur_check
  quality.brightness_check
  duplicate.exact_duplicate_check

required parameters:
  decode_ok
  decode_error
  width
  height
  blur_score
  brightness_score
  content_hash
  exact_duplicate_group_id

required computers:
  image_metadata_computer
  image_quality_computer
  image_hash_computer
  duplicate_group_computer
```

合并规则：

1. 同一个参数字段在一次 run 中只能有一个默认生产者。
2. 一个 `ParameterComputer` 只计算本次被请求的输出列。
3. 图片级 computer 在同一 batch 中共享读取和解码结果。
4. 数据集级 computer 只能依赖已完成阶段的参数、relation 或 artifact。
5. 如果缺少参数生产者，Cleaner 在运行前失败。
6. 如果两个逻辑算子对同一参数提出不兼容的计算配置，Cleaner 在运行前失败。
7. 如果只修改评估配置，不重新计算参数。
8. 如果修改参数计算配置，相关参数列和依赖评估列需要标记为 stale。

## parameter_table 设计

`parameter_table` 是图片级参数宽表，保存客观字段、可复用特征、摘要字段和 artifact 引用。

推荐语义：

```text
一行 = 一张图片
一列或多列 = 图片基础属性、算法参数、派生参数或 artifact 引用
```

基础列：

```text
image_id
image_uri
source_uri
```

典型参数列：

```text
width
height
format
file_size
decode_ok
decode_error
blur_score
brightness_score
contrast_score
content_hash
phash
aspect_ratio
megapixels
exact_duplicate_group_id
near_duplicate_group_id
nearest_neighbor_id
nearest_neighbor_score
cluster_id
outlier_score
embedding_ref
relation_artifact_ref
computed_at
```

字段选择原则：

1. 多个逻辑算子可复用的图片级单值字段放入 `parameter_table`。
2. 大型向量、索引、模型原始输出使用 `artifact_ref`。
3. 一图多关系的 pairwise 结果进入 relation table。
4. `parameter_table` 不保存 action、reason 或 final decision。
5. 参数字段需要记录生产者和计算配置哈希，便于判断是否 stale。

## evaluation_table 设计

`evaluation_table` 是逻辑评估宽表，保存逻辑算子基于参数和策略得到的清洗判断。

推荐语义：

```text
一行 = 一张图片
一列或多列 = 某个逻辑算子的评估输出
```

示例字段：

```text
image_id
image_uri
decode_action
decode_reason
dimension_action
dimension_reason
blur_score
blur_action
blur_reason
brightness_score
brightness_action
brightness_reason
exact_duplicate_group_id
exact_duplicate_action
exact_duplicate_reason
final_action
final_reason
triggered_operator_names
```

宽表保留的原因：

1. Notebook 查看、排序、筛选和导出更直接。
2. 用户不需要理解多张结果表之间的 join。
3. `preview()` 可以直接基于 action 列生成 clean、review、dropped 视图。
4. 第一版更容易测试和验收。

为避免宽表失控，Cleaner 继续维护 `operator_outputs` manifest。

```yaml
operator_outputs:
  quality.blur_check:
    columns:
      - blur_score
      - blur_action
      - blur_reason

  duplicate.exact_duplicate_check:
    columns:
      - exact_duplicate_group_id
      - exact_duplicate_action
      - exact_duplicate_reason
```

## relation 与 artifact

以下结果不进入两张宽表主体：

1. 一张图片对应多个相似图片。
2. 完整 pairwise similarity graph。
3. 聚类内部边关系。
4. embedding 向量文件。
5. ANN index。
6. OCR、caption、视觉模型原始大结果。

relation table 推荐格式：

```text
relation_type
source_image_id
target_image_id
score
group_id
parameter_name
computer_name
artifact_ref
created_at
```

`parameter_table` 只保留摘要字段，例如 `nearest_neighbor_id`、`nearest_neighbor_score`、`cluster_id` 和 `relation_artifact_ref`。

## Cleaner API

v3 继续保持用户 API 简洁：

```python
cleaner = BasicCleaner(
    [
        {"format.decode_check": {}},
        {"size.dimension_check": {"min_width": 224, "min_height": 224}},
        {"quality.blur_check": {"threshold": 80, "action": "review"}},
        {"duplicate.exact_duplicate_check": {"action": "drop"}},
    ]
)

cleaner.run(dataset)
cleaner.state()
cleaner.preview()
cleaner.config(
    [
        {"quality.blur_check": {"threshold": 120, "action": "drop"}},
    ]
)
cleaner.rerun(
    [
        {"quality.blur_check": {"threshold": 120, "action": "drop"}},
    ]
)
cleaner.export(kind="clean", path="clean.parquet")
```

`config()` 和 `rerun()` 需要区分两类变化：

1. 评估配置变化：阈值、action、reason 规则。这类变化只重算 `evaluation_table`。
2. 参数计算配置变化：hash 算法、resize 策略、embedding 模型、聚类参数。这类变化重算相关参数列，并级联重算依赖的评估列。

## preview 与 export

`preview()` 不产生新的正式数据集，只基于 `evaluation_table` 返回当前策略下的视图统计和样本预览。

建议输出：

```text
total_count
clean_count
review_count
dropped_count
restricted_count
operator_summary
sample_rows
```

`export()` 负责生成正式 Parquet 数据集。支持类型：

```text
clean
dropped
review
full
parameters
evaluations
```

`full` 必须保留全部图片。`clean`、`dropped`、`review` 基于 `final_action` 或指定策略生成子集。`dropped` 和 `review` 必须保留 `final_reason` 与 `triggered_operator_names`，便于追溯。

## 与其他模块边界

1. 清洗平台读取 Dataset，不修改 raw Dataset。
2. 图片主引用仍然是 `image_uri`，图片资产仍由 Storage 管理。
3. `parameter_table`、`evaluation_table`、relation table 和 export 结果使用 Parquet。
4. SQLite 只保存运行状态、配置快照和产物索引，不保存大规模图片级明细。
5. 数据集可视化模块可以直接读取 `evaluation_table` 和导出视图进行展示。
6. 错误处理与恢复模块只负责 run state、配置哈希、产物路径和恢复校验。
7. 算子命名继续按能力组织，不按底层库或算法实现组织。

## 与 v2 的主要差异

1. v2 的 `BackendAdapter` 被 v3 的 `ParameterComputer` 取代。
2. v2 按 backend 分组运行，v3 按参数需求和计算阶段组织运行。
3. v2 允许 fastdup adapter，v3 完全移除 fastdup。
4. v2 更接近“逻辑算子映射唯一后端”，v3 改为“逻辑算子声明参数需求，参数计算单元统一生产”。
5. v2 只要求同一 backend 避免重复执行，v3 要求同一 batch 内共享图片读取和解码。
6. v2 的 relation/artifact 主要用于承接工具输出，v3 的 relation/artifact 用于承接自研全局计算结果和大型中间产物。

## 从 v2 到 v3 的迁移计划

迁移建议分三步进行：

1. 删除 fastdup 后端、注册项和相关占位测试，第一版只保留可自研实现的内置算子。
2. 将 `BackendAdapter`、`BackendOperatorRequest`、`BackendResult` 迁移为 `ParameterComputer`、`ParameterRequest`、`ParameterResult`。
3. 将 `BasicCleaner` 的执行流程从按 backend 分组调整为按 compute stage 分组：image batch -> table derived -> dataset global -> evaluation。

迁移过程中保持用户 API 不变，避免 Notebook 和示例入口频繁变化。

## 非目标

v3 第一版不做以下事情：

1. 不引入 fastdup、CleanVision 或其他偏集成式清洗框架。
2. 不实现通用 DAG、Graph Runtime 或重型 Planner。
3. 不做多个候选计算实现的自动选择。
4. 不实现跨 run、跨数据集的全局缓存系统。
5. 不把 embedding、ANN index 或 pairwise graph 强塞进宽表。
6. 不把大规模图片级明细写入 SQLite。
7. 不在检测类算子中直接修改、删除或转换图片资产。
8. 不为尚未出现的业务场景提前设计宽泛插件系统。

## 设计取舍

v3 的核心取舍是把“新增算子时的易理解性”和“批量计算时的性能复用”同时保留下来。

逻辑算子仍然是用户和业务文档的中心，新增能力时先思考“这个检查需要哪些参数、如何评估”。`ParameterComputer` 是平台内部的参数生产层，负责把多个逻辑算子的参数需求合并到一次批量读取和计算中。

这种设计比“每个逻辑算子自己读取图片并计算”更能控制 IO 和解码成本，也比“所有计算方法集中在一个巨大计算层、逻辑算子只做映射”更容易维护清洗语义。第一版只做轻量 `ComputePlan`，不追求全局最优调度；当后续出现多 Cleaner、跨 run 复用和大规模分布式执行需求时，再考虑更强的执行层。
