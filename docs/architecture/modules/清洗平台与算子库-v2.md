# 清洗平台与算子库架构 v2

本文档是清洗平台与算子库的新版本设计。原 `清洗平台与算子库.md` 保持不变，本文档用于承载尚未实现前的破坏式调整。

## 模块定位

清洗平台负责基于 raw Dataset 执行一组图片清洗逻辑算子，生成图片级参数表、图片级评估表和必要的关系类产物，并支持用户在 Notebook 或 Python API 中查看、调整、预览和导出清洗结果。

v2 设计放弃重型执行规划模型，不再引入 `CleaningRecipe`、`ExecutionPlanner`、`ExecutionPack`、`ResultNormalizer` 这类平台级编排对象。第一版目标是让清洗能力更接近 fastdup 的使用体验：

```text
Dataset
  -> Cleaner([{operator_name: config}, ...])
  -> run()
  -> parameter_table
  -> evaluation_table
  -> preview() / state() / export()
```

清洗平台对用户暴露的是“要检查什么能力”，例如 `quality.blur_check`、`duplicate.near_duplicate_check`，而不是直接暴露 OpenCV、fastdup、CleanVision 等底层工具名称。

## 核心原则

1. Cleaner 是用户侧主要入口，负责承载一类清洗策略。
2. 逻辑算子按能力命名，不按底层工具命名。
3. 每个逻辑算子只映射一个明确物理后端，不做多个候选后端和执行规划。
4. 逻辑算子实现保持很薄，只描述字段需求、后端映射、评估规则和输出列。
5. `BasicCleaner` 第一版就按 `backend_name` 对逻辑算子分组运行，避免同一后端重复读取、重复解码或重复执行 fastdup。
6. 后端负责计算参数、特征、分组、分数和后端原生判断；逻辑算子负责生成平台统一的 action、reason 和评估输出列。
7. 清洗过程主要维护两张宽表：`parameter_table` 和 `evaluation_table`。
8. Notebook 查看体验优先，图片级结果默认合并为一行一图的大表。
9. 复杂 pair、group、graph 类结果不强行塞进宽表，使用 relation table 或 artifact 引用。
10. Parquet 存数据平面结果，SQLite 只存运行状态、配置快照和产物引用，图片本体仍然存 Storage。
11. raw Dataset 在清洗过程中保持不可变，clean、dropped、full 都是基于评估表生成的导出视图。

## 核心对象

v2 清洗平台只保留少量核心对象：

1. `Cleaner`：清洗策略基类或协议，定义 `run`、`preview`、`state`、`config`、`rerun`、`export` 等用户侧能力。
2. `BasicCleaner`：第一版基础清洗策略，覆盖解码、尺寸、质量、基础重复、基础敏感等通用清洗能力。
3. `OperatorSpec`：逻辑算子规格，声明算子名称、输入字段、输出列、默认配置、唯一后端和平台评估函数。
4. `OperatorRegistry`：维护 `operator_name` 到 `OperatorSpec` 的映射。
5. `BackendAdapter`：对接 OpenCV、fastdup、Pillow、CleanVision 或自研算法，把底层输出归一化为参数字段、关系表和 artifact。
6. `CleanerRunState`：记录 run_id、输入 dataset 指纹、启用算子、配置快照、输出表路径和运行摘要。

## Cleaner 类型

`Cleaner` 表示一类清洗策略，而不是一个通用执行图。不同 Cleaner 可以复用同一套逻辑算子注册和后端 adapter，但默认启用的算子、评估策略和导出策略可以不同。

建议第一阶段定义：

```text
Cleaner
  BasicCleaner
```

后续可以扩展：

```text
NsfwCleaner
WatermarkCleaner
TextImageCleaner
ProductImageCleaner
```

`BasicCleaner` 主要承载初步清洗策略，包括基础解码、尺寸、模糊、低质、重复、异常内容等。更复杂的业务场景不需要塞进 `BasicCleaner`，可以通过新的 Cleaner 类型表达。

## Cleaner API

Cleaner 面向 Notebook 和 Python package 使用，API 应保持直接、可读和可组合。

示例：

```python
cleaner = BasicCleaner(
    [
        {
            "format.decode_check": {},
        },
        {
            "size.dimension_check": {},
        },
        {
            "quality.blur_check": {
                "threshold": 80,
                "action": "drop",
            },
        },
        {
            "duplicate.near_duplicate_check": {
                "threshold": 0.95,
                "action": "review",
            },
        },
    ]
)

cleaner.run(dataset)
cleaner.state()
cleaner.preview()
cleaner.config(
    [
        {
            "quality.blur_check": {
                "threshold": 100,
                "action": "drop",
            },
        },
    ]
)
cleaner.rerun(
    [
        {
            "duplicate.near_duplicate_check": {
                "threshold": 0.98,
                "action": "review",
            },
        },
    ]
)
cleaner.export(kind="clean", path="clean.parquet")
```

Cleaner 构造入参、`config` 和 `rerun` 使用同一种算子配置结构：

```python
[
    {
        "quality.blur_check": {
            "threshold": 80,
            "action": "drop",
        }
    },
]
```

核心方法：

1. `run(dataset)`：执行启用算子，补齐参数表字段，生成或更新评估表列。
2. `preview()`：基于当前评估表预览 clean、review、dropped 等结果，不修改 raw Dataset。
3. `state()`：打印运行矩阵，包括每个算子的完成状态、命中数量、失败数量和建议动作分布。
4. `config(operator_configs)`：接收 `list[{operator_name: config}]`，重新配置一个或多个算子的策略，并标记相关评估列需要重算。
5. `rerun(operator_configs)`：接收 `list[{operator_name: config}]`，对指定算子使用新配置重新计算参数字段和评估列。
6. `result(operator_name)`：查看单个算子的评估结果列和相关图片。
7. `export(kind, path)`：导出 `clean`、`dropped`、`full`、`parameters`、`evaluations` 等 Parquet 结果。

`config` 和 `rerun` 需要区分两类变化：

1. 评估参数变化，例如阈值、动作策略、是否进入 dropped。这类变化通常只需要重算 `evaluation_table` 的相关列。
2. 运算参数变化，例如 embedding 模型、hash 算法、fastdup 运行参数。这类变化需要重算 `parameter_table` 的相关字段，并级联更新评估列。

`config` 只更新配置和失效标记，不主动执行重算；`rerun` 会立刻对传入算子执行重新计算。两者都使用同一种 `list[{operator_name: config}]` 入参，避免 Cleaner 初始化、配置更新和局部重跑出现三套不同接口。

## 逻辑算子设计

逻辑算子是用户侧稳定能力单元，但不是重型执行节点。单个逻辑算子只做四件事：

1. 声明算子名称。
2. 声明需要读取或生成的参数字段。
3. 声明唯一物理后端。
4. 声明评估表输出列和默认判断规则。

`OperatorSpec` 不保存用户输入配置。用户传入的 `list[{operator_name: config}]` 属于某一次 Cleaner 运行的实例配置，由 Cleaner 解析、合并默认配置并保存到运行状态中。执行时，`OperatorSpec.default_config` 与用户配置合并后传给 backend 和 evaluator。

逻辑算子的评估函数负责平台清洗决策：把 `parameter_table` 中的参数、后端原生标签或分数转换成 `evaluation_table` 中统一的 action、reason、score、label 等列。后端可以产出 fastdup 原生分组、相似度、离群分数或标签，但不直接决定 `final_action`。

示例：

```text
quality.blur_check
  parameter_inputs:
    - blur_score
  backend:
    opencv_blur_backend
  evaluation_outputs:
    - blur_score
    - blur_action
    - blur_reason

duplicate.near_duplicate_check
  parameter_inputs:
    - near_duplicate_group_id
    - near_duplicate_score
    - near_duplicate_representative_id
  backend:
    fastdup_similarity_backend
  evaluation_outputs:
    - near_duplicate_group_id
    - near_duplicate_score
    - near_duplicate_action
    - near_duplicate_reason
```

逻辑算子不负责：

1. 自己读取原始图片。
2. 自己管理批处理和中间目录。
3. 自己决定全局 clean、dropped、full。
4. 自己选择多个候选后端。
5. 自己维护跨算子的执行顺序。

## 算子到后端映射

v2 不做后端候选和 Planner 编排。每个逻辑算子在当前版本中只有一个明确后端。

示例映射：

```text
format.decode_check
  -> pillow_decode_backend

size.dimension_check
  -> pillow_metadata_backend

quality.blur_check
  -> opencv_blur_backend

quality.brightness_check
  -> opencv_brightness_backend

duplicate.exact_duplicate_check
  -> image_hash_backend

duplicate.near_duplicate_check
  -> fastdup_similarity_backend

distribution.outlier_check
  -> fastdup_outlier_backend

distribution.cluster_check
  -> fastdup_cluster_backend
```

`BasicCleaner` 在第一版就需要按 `backend_name` 对逻辑算子分组运行。同一后端一次接收多个逻辑算子的参数计算请求，例如 `distribution.outlier_check`、`distribution.cluster_check` 和 `duplicate.near_duplicate_check` 可以在一次 fastdup 后端运行中补齐各自需要的参数字段。

这种分组能力不提升为平台级 Planner。平台只负责把同一后端的逻辑算子请求合并传给对应 adapter；adapter 负责复用底层读取、解码、fastdup 运行或 artifact，并把平台需要的稳定字段写入 `parameter_table` 或 relation/artifact 产物。`evaluation_table` 由逻辑算子的评估函数生成。

## parameter_table 设计

`parameter_table` 是图片级参数宽表，保存图片解析和算法运算过程中产生的客观事实、特征和可复用中间结果。

它不是用户配置表，也不是单个算子的最终判断表。

推荐语义：

```text
一行 = 一张图片
一列或多列 = 图片基础属性、特征、算法中间结果或 artifact 引用
```

典型字段：

```text
image_id
image_uri
source_uri
width
height
format
file_size
content_hash
phash
blur_score
brightness_score
contrast_score
embedding_ref
caption
ocr_text
near_duplicate_group_id
nearest_neighbor_id
nearest_neighbor_score
cluster_id
outlier_score
computed_at
```

字段选择原则：

1. 可以被多个算子复用的客观字段放入 `parameter_table`。
2. 图片级单值结果优先放入 `parameter_table`。
3. 大型向量、索引、第三方工具原始输出使用 `artifact_ref` 指向外部产物。
4. 一图多关系的 pairwise 结果不要强塞进宽表，应放入 relation table 或 artifact。

fastdup 这类工具的原始输出需要通过 `BackendAdapter` 归一化后进入平台表。平台不要求 fastdup 天然输出 `parameter_table`，只要求 adapter 能把平台关心的稳定字段写回来。

## evaluation_table 设计

`evaluation_table` 是图片级评估宽表，保存逻辑算子基于参数和策略得到的清洗判断结果。

`evaluation_table` 不直接承接后端原始输出。后端输出先进入 `parameter_table`、relation table 或 artifact；逻辑算子再根据合并后的配置和参数字段生成评估列。这样可以在只修改阈值、动作策略或 reason 规则时重算评估列，而不必重新运行 fastdup、OpenCV 或其他后端。

推荐语义：

```text
一行 = 一张图片
一列或多列 = 某个算子的评估输出
```

示例字段：

```text
image_id
image_uri
decode_action
decode_reason
dimension_action
dimension_reason
blur_score
blur_action
blur_reason
near_duplicate_group_id
near_duplicate_score
near_duplicate_action
near_duplicate_reason
sensitive_score
sensitive_label
sensitive_action
final_action
final_reason
triggered_operator_names
```

宽表设计的主要原因：

1. Notebook 中查看、筛选、排序和导出更直观。
2. `preview()` 可以直接基于多个 action 列生成 clean、review、dropped 视图。
3. 用户不需要理解多个算子表之间的 join 关系。
4. 第一版实现更简单，验证路径更短。

为避免宽表失控，Cleaner 需要维护 `operator_outputs` manifest，记录每个算子拥有的输出列。

示例：

```yaml
operator_outputs:
  quality.blur_check:
    columns:
      - blur_score
      - blur_action
      - blur_reason

  duplicate.near_duplicate_check:
    columns:
      - near_duplicate_group_id
      - near_duplicate_score
      - near_duplicate_action
      - near_duplicate_reason
```

当用户调用 `result("quality.blur_check")`、`config([{"quality.blur_check": {...}}])` 或 `rerun([{"quality.blur_check": {...}}])` 时，Cleaner 通过 manifest 定位需要读取、覆盖或失效的列。

## relation 与 artifact 产物

并非所有结果都适合进入两张宽表。以下结果应使用 relation table 或 artifact：

1. 一张图片对应多个相似图片。
2. 完整 pairwise similarity graph。
3. 聚类内部所有边关系。
4. fastdup 原始报告目录。
5. embedding 向量文件和 ANN index。
6. 大型 OCR、caption、视觉模型中间产物。

建议 relation table：

```text
operator_name
source_image_id
target_image_id
relation_type
score
group_id
artifact_ref
created_at
```

宽表只保留摘要字段，例如 `near_duplicate_group_id`、`nearest_neighbor_id`、`nearest_neighbor_score` 和 `relation_artifact_ref`。

## 运行状态与产物组织

数据平面产物建议使用 Parquet，运行状态和配置快照使用 SQLite 或 JSON manifest。

推荐目录：

```text
cleaning_outputs/
  {run_id}/
    parameter_table.parquet
    evaluation_table.parquet
    operator_outputs.yaml
    relations/
      duplicate.near_duplicate_check.parquet
    artifacts/
      fastdup/
      embeddings/
    state.json
```

`state.json` 或 SQLite run state 至少记录：

```text
run_id
dataset_fingerprint
cleaner_type
enabled_operator_configs
operator_config_hashes
parameter_table_path
evaluation_table_path
operator_outputs_path
artifact_paths
started_at
finished_at
status
```

## preview 与 export

`preview()` 不产生新的正式数据集，只基于 `evaluation_table` 返回当前策略下的视图统计和样本预览。

建议输出：

```text
total_count
clean_count
review_count
dropped_count
restricted_count
operator_summary
sample_rows
```

`export()` 负责生成正式 Parquet 数据集。支持类型：

```text
clean
dropped
review
full
parameters
evaluations
```

`full` 必须保留全部图片，`clean`、`dropped`、`review` 是基于 `final_action` 或指定策略生成的子集。`dropped` 必须保留 `final_reason` 和 `triggered_operator_names`，便于追溯。

## 初版算子清单

`BasicCleaner` 初版建议覆盖以下能力：

```text
format.decode_check
size.dimension_check
quality.blur_check
quality.brightness_check
quality.contrast_check
duplicate.exact_duplicate_check
duplicate.near_duplicate_check
distribution.outlier_check
distribution.cluster_check
content.blank_image_check
```

功能分类仍按能力组织：

1. `format`：格式、解码、文件损坏。
2. `size`：宽高、长宽比、最小尺寸、最大尺寸。
3. `quality`：模糊、亮度、对比度、噪声、灰度、纯色。
4. `duplicate`：完全重复、近似重复、重复组。
5. `distribution`：离群、聚类、语义分布。
6. `content`：空白图、异常内容、合规风险。
7. `feature`：hash、embedding、caption、OCR 等特征生成。

检测类算子只产生评估和建议动作，不直接删除或改写图片资产。检测所需参数由对应后端写入 `parameter_table`。

## 与其他模块边界

1. 清洗平台读取 Dataset，不修改 raw Dataset。
2. 图片主引用仍然是 `image_uri`，图片资产仍由 Storage 管理。
3. `parameter_table`、`evaluation_table`、relation table 和 export 结果使用 Parquet。
4. SQLite 只保存运行状态、配置快照和产物索引，不保存大规模图片级明细。
5. 数据集可视化模块可以直接读取 `evaluation_table` 和导出视图进行展示。
6. 错误处理与恢复模块只负责 run state、配置哈希、产物路径和恢复校验。

## 非目标

v2 第一版不做以下事情：

1. 不实现通用 DAG 或 Graph Runtime。
2. 不实现 `ExecutionPlanner`、`ExecutionPack` 和复杂后端选择。
3. 不让用户直接按 OpenCV、fastdup、CleanVision 配置算子名称。
4. 不为每个逻辑算子默认创建独立结果表。
5. 不把大规模图片级结果写入 SQLite。
6. 不在检测类算子中直接修改、删除或转换图片资产。
7. 不为尚未出现的业务场景提前设计宽泛插件系统。

## 设计取舍

v2 的核心取舍是放弃平台级全局最优执行规划，换取第一版的可理解、可实现和可验证。

第一版保留 `BasicCleaner` 内部的轻量 backend 分组运行：同一 backend 的多个逻辑算子会合并成一次 adapter 调用。只有当这种分组无法满足多个 Cleaner、多个 run 和跨数据集缓存需求时，再考虑引入更强的执行层。
