# 图片导入与元数据架构

本文档从总架构文档中拆分而来，承接对应功能域的详细架构设计。总架构文档只保留总体把控、模块边界和跨模块约束。

## 模块定位

图片导入与元数据模块负责把外部图片接入平台统一存储，提取基础图片信息，并生成可被后续清洗、查看和导出的 raw 数据集。

## 职责范围

1. 扫描或读取本地目录、局域网文件系统、对象存储、URL 清单和已有数据集文件。
2. 调用存储系统把图片写入具名后端存储库，并生成 image_uri。
3. 提取基础图片元数据，生成 raw dataset 和导入报告。
4. 支持用户在导入任务创建时指定全局 tags，用于标记整个导入数据集。
5. 记录导入失败清单、来源追溯字段和 URL 导入安全约束。

## 核心对象

1. Source Reader
2. Storage Writer
3. Basic Metadata Extractor
4. Raw Dataset Builder
5. Import Report Builder
6. failure_manifest

## 核心流程

外部数据来源 -> Source Reader -> Storage Adapter -> 平台统一存储 -> Basic Metadata Extractor -> Raw Dataset Builder -> Import Report Builder。

## 数据 / 状态 / 配置契约

1. raw dataset 必须包含 image_id、source_uri、source_type、source_file_name、storage_name、image_uri、file_size_bytes、image_content_hash、文件格式字段、图片基础字段、EXIF/GPS 扩展字段、import_status、imported_at、schema_version、tags 等字段。
2. source_uri 是审计字段，平台内部 raw/full 可以保留；对外共享、训练导出和静态报告默认不输出。
3. tags 是路径型层级标签列表，保存在 raw dataset 中；每个路径前缀都可作为后续筛选节点。
4. 导入配置归属本模块，包括 source_type、source_uri/list、import_mode、copy/reference/copy_on_write、overwrite、URL 下载限制、global_tags 和导入输出位置。

## 与其他模块边界

1. 依赖存储系统写入图片和解析地址，但不直接依赖具体文件系统或 MinIO SDK。
2. 输出 raw dataset 给数据集管理和清洗平台，不执行清洗算法。
3. 元数据只记录事实，不做 clean/dropped 判定。

## V1 范围与非目标

1. V1 支持本地目录、已有数据集文件和基础 URL 清单导入。
2. V1 不实现在线标注、多人协作、复杂数据治理和完整数据集版本管理。

## 详细设计

### 7. 图片导入模块设计

#### 7.1 模块定位

图片导入模块负责把外部图片来源纳入平台统一管理。它不是简单生成图片清单，而是需要把图片写入具名后端存储库，并以 image_uri 作为后续清洗、增强和可视化的主引用。

#### 7.2 职责范围

图片导入模块负责：

1. 接收外部数据来源，包括本地目录、局域网文件系统、对象存储、URL 清单和已有数据集文件。
2. 扫描或读取图片条目。
3. 调用存储系统接入层，把图片写入具名后端存储库。
4. 为导入后的图片生成 image_uri。
5. 保留原始来源地址，用于后续追溯。
6. 提取基础图片信息。
7. 把用户指定的 global_tags 写入 raw 原始数据集。
8. 输出导入报告和失败图片清单。

图片导入模块不负责：

1. 直接绑定 MinIO SDK 或文件系统细节。
2. 执行损坏检测、重复检测、质量检测等清洗算法。
3. 管理 CleaningRecipe、ExecutionPlan 或 ExecutionPack 的执行细节。
4. 决定 clean、dropped、full 数据集输出规则。

#### 7.3 导入后的唯一真相源

外部图片导入受管存储后，受管存储中的图片作为唯一真相源。后续清洗、增强、可视化和训练导出都应基于 image_uri 访问图片。

原始来源地址只用于追溯和审计，不作为后续处理读取来源。这样可以避免原始文件移动、URL 失效、局域网路径不可访问或外部权限变化导致后续任务不可复现。

第一版需要区分三种导入模式：

1. copy：把外部图片复制到平台统一存储，适用于 URL、外部目录和需要归档的数据源。
2. reference：平台只登记已受管存储中的对象，不重复复制，适用于已经位于平台接入存储库中的对象。
3. copy_on_write：初始引用外部对象，只有在需要生成派生产物或迁移归档时复制。

无论采用哪种模式，raw 数据集中的主引用都必须是 image_uri。Source Reader 需要输出稳定的 SourceRecord，导入幂等键建议由 source_uri、source_etag 或 image_content_hash、import_run_id 组合生成。Storage Writer 在复制或登记对象时应同步计算 image_content_hash，避免后续为哈希重复读取整文件。

#### 7.4 地址模型

图片导入模块需要同时处理两类地址：

1. source_uri：原始来源地址，用于追溯。
2. image_uri：当前运行环境下可访问的绝对地址，写入平台数据集，作为后续处理的主引用。

平台内部数据集默认保存 image_uri，不再额外保存 storage_path 或 resolved_uri。对外共享默认不输出 source_uri；如需隐藏真实存储位置，可以在导出阶段另行复制图片或生成脱敏后的导出版地址。

#### 7.5 导入 tags

导入任务可以接收用户手动指定的 global_tags，用于标记整个导入数据集。例如：

```text
dataset/project_a
source/customer_x
batch/2026-07-02
```

Raw Dataset Builder 负责把 global_tags 写入 raw dataset 每一行的 tags 字段：

```text
tags = unique(global_tags)
```

写入时保持 global_tags 的稳定顺序，重复 tag 只保留第一次出现的值。raw dataset 只存用户实际赋予的 tag path，不自动展开父级；无标签图片写入空列表。global_tags 会复制到每张图片的 tags 列，保证 raw Parquet 自包含，后续筛选、数据集合并和导出不需要额外读取导入配置或 metadata 文件。

tags 字段名固定为 tags，不使用 rags。第一版不从目录名、文件名、已有数据集列、URL 清单字段或来源上下文自动提取 tags，也不建立独立 tag 表、tag catalog 或 SQLite 图片级 tag 明细；如后续需要支持来源标签抽取，可单独设计 tag extraction 或导入 metadata。

#### 7.6 导入运行状态与报告

图片导入模块自己组织 Source Reader、Storage Writer、Basic Metadata Extractor、Raw Dataset Builder 和 Import Report Builder 的顺序流程。

导入模块可以复用 Run State Store 记录轻量运行状态，例如 import_run、import_progress、import_artifact 和 import_failed_summary。这些状态用于导入续跑、进度查看、失败样本重试和 raw Dataset 产物追踪。图片级元数据明细仍然写入 raw Parquet，导入失败明细可以写入失败清单文件；SQLite 不作为导入图片明细表使用。

#### 7.7 失败处理

导入过程中，单张图片失败不应中断整个导入任务。失败图片需要记录：

1. 原始来源地址。
2. 失败阶段。
3. 失败原因。
4. 必要的错误上下文。

失败清单作为导入阶段的标准输出产物之一。

#### 7.8 URL 导入安全边界

URL 导入第一版必须采用最小安全治理：

1. 默认只允许 http 和 https，其中生产环境建议只允许 https。
2. 默认拒绝 localhost、内网网段、链路本地地址和云元数据地址。
3. 限制重定向次数、单文件大小、单任务总下载量和下载超时。
4. 先校验 Content-Type、文件扩展名和文件魔数，再写入正式存储。
5. 下载过程不透传本地 Cookie、云凭据或对象存储凭据。
6. URL 导入失败必须进入 failure_manifest，不应产生不可追踪的孤儿对象。

### 13. 元数据设计

#### 13.1 模块定位

本章描述图片导入阶段的基础元数据抽取设计。元数据抽取节点对应导入流程中的 Basic Metadata Extractor，用于为 raw 原始数据集生成图片级基础信息。

导入阶段元数据抽取的目标是：

1. 形成 raw 原始数据集所需的图片级明细。
2. 保留图片来源追溯信息。
3. 保留 image_uri 图片主引用。
4. 提供后续清洗、可视化和导出的基础字段。

导入阶段元数据抽取不做清洗决策。损坏检测、重复检测、质量评分、内容风险识别等能力由清洗算子负责。

#### 13.2 存储原则

第一版元数据全部写入 Parquet 数据集文件，作为 raw 原始数据集的一部分。

数据库暂不保存图片级数据集元数据信息。也就是说，数据库第一版不承载每张图片的 width、height、image_format、source_uri、image_uri 等明细字段。

推荐原则：

1. raw Parquet 是图片级元数据事实表。
2. 数据库暂不存储图片级元数据明细。
3. Run State Store 只保存 raw 数据集文件的引用地址、行数、字段摘要和生成状态。
4. 后续清洗流程从 raw Parquet 读取 dataset_raw。
5. 后续如需要提升可视化查询性能，再讨论是否把少量高频索引字段同步到数据库。

#### 13.3 元数据抽取范围

导入阶段应优先抽取低成本、稳定、可复用的基础元数据。第一版建议按以下类别组织。

##### 标识类元数据

用于在平台内部唯一定位图片及其导入上下文。

```text
image_id
import_run_id
dataset_id
source_record_id
```

##### 来源类元数据

用于追溯图片导入前的来源。

```text
source_uri
source_type
source_name
source_relative_path
source_file_name
source_extension
source_last_modified
source_size_bytes
```

source_uri 只用于追溯和审计，不作为后续处理的主读取地址。

##### 存储类元数据

用于后续通过 Storage 系统访问图片。

```text
storage_name
image_uri
object_path
storage_size_bytes
storage_etag
image_content_hash
imported_at
```

image_uri 是平台内部数据集中的主引用地址。后续清洗、增强、可视化和导出默认基于 image_uri 访问图片。storage_name 和 object_path 用于受管存储定位和后续迁移辅助，不作为第二套图片主地址。

##### 文件基础属性

用于描述导入后图片文件的基础文件信息。

```text
file_name
file_extension
file_size_bytes
mime_type
magic_type
image_content_hash
```

image_content_hash 可用于导入幂等、来源审计和后续重复检测的候选输入，但导入阶段不根据 image_content_hash 直接做最终重复判定。

##### 图片基础属性

用于描述图片本身的轻量基础信息。

```text
width
height
pixel_count
aspect_ratio
orientation
channels
color_mode
image_format
bit_depth
has_alpha
animated
frame_count
icc_profile_present
dpi_x
dpi_y
```

这些字段可以通过读取图片头信息或轻量解码获得。它们可支持后续尺寸检查、格式检查、可视化筛选和数据集统计。

##### 标签类元数据

用于描述用户在导入任务上指定的全局路径型标签。

```text
global_tags
tags
```

global_tags 来自导入配置，表示用户为整个导入数据集指定的标签。tags 是写入 raw dataset 的最终标签列表，第一版直接由 global_tags 去重后生成，并复制到每张图片行。

标签类元数据只记录用户输入的数据集标记，不记录损坏、重复、质量、敏感内容等清洗判断，也不重复承载已有 raw 字段已经表达的事实。

##### EXIF 与嵌入信息

EXIF 信息不是所有图片都有，第一版可以作为可选扩展元数据抽取。

```text
exif_datetime
camera_make
camera_model
gps_latitude
gps_longitude
exif_orientation
software
```

EXIF 字段差异较大，缺失属于正常情况，不应影响导入任务整体成功。

##### 导入处理状态

用于记录导入和元数据抽取过程中的状态。

```text
import_status
import_error_code
import_error_message
metadata_extract_status
metadata_extract_error
metadata_warnings
```

导入失败不应中断整批任务。失败图片需要进入失败清单；可导入但元数据存在警告的图片，应保留在 raw 数据集中并记录 metadata_warnings。

#### 13.4 第一版最小字段集

第一版 raw 数据集至少应包含以下字段：

```text
image_id
source_uri
source_type
source_file_name
storage_name
image_uri
file_size_bytes
image_content_hash
file_extension
mime_type
image_format
width
height
pixel_count
aspect_ratio
orientation
channels
color_mode
has_alpha
animated
frame_count
icc_profile_present
dpi_x
dpi_y
exif_orientation
exif_datetime
camera_make
camera_model
gps_present
gps_latitude
gps_longitude
import_status
imported_at
schema_version
tags
```

这些字段可以支撑图片唯一定位、来源追溯、受管存储访问、基础筛选和后续清洗输入。

tags 字段保存图片关联的路径型层级标签列表。每个 tag path 使用 `/` 分隔层级，例如 `scene/indoor`、`scene/kitchen/cook` 或 `quality/blur`。每一级都视为可筛选标签节点，因此 `scene/kitchen/cook` 可被 `scene`、`scene/kitchen` 和 `scene/kitchen/cook` 三种前缀筛选命中。raw 数据集只存实际赋予的 tag path，不自动展开父级；无标签图片写入空列表。

导入任务创建时指定的 global_tags 会复制到每张图片的 tags 列。例如用户指定 `dataset/project_a` 和 `source/customer_x`，则每张图片的 tags 为：

```text
["dataset/project_a", "source/customer_x"]
```

这个设计让 raw Parquet 在数据集合并时保持自包含，不需要额外读取导入配置即可知道图片来自哪个数据集、批次或来源标记。

#### 13.5 可空扩展字段

以下字段已经进入 raw required columns，但不是所有图片都包含对应信息；缺失时字段保留，值为 None 或明确布尔值。

```text
icc_profile_present
dpi_x
dpi_y
exif_orientation
exif_datetime
camera_make
camera_model
gps_present
gps_latitude
gps_longitude
```

EXIF/GPS 缺失或解析失败不应影响 raw 数据集的基本生成流程。gps_latitude 和 gps_longitude 属于敏感字段，对外导出时需要显式脱敏或移除。

#### 13.6 与清洗算子的边界

导入阶段元数据抽取只负责基础事实记录，不负责判断图片是否应该保留或丢弃。

以下能力不属于导入阶段元数据抽取：

1. 损坏图片判定。
2. 重复图片分组。
3. 模糊、亮度、噪声等质量评分。
4. 敏感内容或异常内容识别。
5. clean、dropped、full 数据集判定。

如果导入阶段发现图片无法读取基础头信息，可以记录 metadata_extract_status 和 metadata_extract_error，但最终是否丢弃由后续清洗算子和归并策略决定。

#### 13.7 设计原则

1. 元数据优先进入 raw Parquet，不进入数据库明细表。
2. 导入阶段抽取低成本、稳定、可复用的基础信息。
3. image_uri 是后续处理的主引用，source_uri 只用于追溯。
4. 导入阶段不做清洗决策。
5. 元数据缺失或 EXIF 缺失不应导致整批导入失败。
6. 单张图片元数据抽取失败应记录错误，并进入导入报告或失败清单。
