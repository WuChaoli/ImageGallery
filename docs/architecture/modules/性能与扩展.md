# 性能与扩展架构

本文档从总架构文档中拆分而来，承接对应功能域的详细架构设计。总架构文档只保留总体把控、模块边界和跨模块约束。

## 模块定位

性能与扩展模块定义第一版十万级可用、百万级预留的批处理、分片、物理执行融合、artifact 复用、并行、I/O 控制和后续演进策略。

## 职责范围

1. 定义数据规模假设、批处理策略、Parquet 分片和扫描策略。
2. 控制图片读取、解码、缩略图生成、MinIO 请求和 SQLite 写入边界。
3. 描述 ExecutionPack 的批处理、staged 执行、共享 artifact 和 I/O 控制策略。
4. 记录后续成本优化器、分布式、增强、语义检索和版本治理演进方向。

## 核心对象

1. batch_config
2. batch reader
3. Parquet part files
4. ExecutionPack worker pool
5. I/O limiter
6. Artifact cache
7. Feature table
8. thumbnail cache

## 核心流程

Dataset scan -> ExecutionPlanner -> batch reader -> ExecutionPack 融合执行 -> artifact / result 分片写出 -> manifest 提交 -> ResultNormalizer -> 抽样可视化/报告。

## 数据 / 状态 / 配置契约

1. 性能配置归属本模块，包括 batch_size、write_batch_size、max_workers、in_flight_bytes、MinIO 并发、缩略图数量、报告抽样限制、artifact 复用策略和 ExecutionPack 并行限制。
2. raw、pack_artifact、node_result、node_status_matrix、merge_result 和导出数据集默认支持 Parquet 分片。
3. 图片增强不作为 V1 独立模块实现，只在后续演进中复用 storage、dataset、graph、state、visualization 和 cleaning artifact 能力。

## 与其他模块边界

1. 性能模块定义约束和策略，不直接实现业务功能。
2. 具体 batch、stage、pack 执行由清洗平台实现。
3. 具体存储和 I/O 能力由存储系统提供。
4. artifact 可复用性校验由错误处理与恢复模块和 ArtifactRegistry 共同承担。

## V1 范围与非目标

1. V1 面向十万级图片数据集可用，并为百万级扩展预留空间。
2. V1 支持单机内的基础 ExecutionPack 融合和 artifact 复用。
3. V1 不承诺所有算子百万级生产性能，不引入分布式计算框架。
4. V1 不实现复杂跨机器成本优化器。

## 详细设计

### 15. 图片增强设计

本次不实现图片增强模块，本章暂不展开。

图片增强可以作为后续能力在同一套存储、数据集文件、运行状态、清洗 artifact 和可视化能力之上扩展。当前技术架构讨论聚焦图片导入、清洗、数据集输出和可视化查看。

### 18. 性能与扩展性设计

#### 18.1 设计目标

第一版需要面向十万级图片数据集可用，并在架构上为百万级图片数据集预留扩展空间。

性能设计的核心原则是：

```text
共享计算优先
流式读写
批处理
结果落盘
状态轻量化
全局算子 staged 执行
```

系统不应假设全量图片、全量元数据、全量执行包产物、全量逻辑算子结果或全量状态矩阵可以一次性加载到内存。

#### 18.2 数据规模假设

第一版按以下数据规模进行设计：

1. 小规模：千级图片，用于本地开发、单元测试和 Notebook 调试。
2. 中规模：十万级图片，是第一版主要可用目标。
3. 大规模：百万级图片，第一版架构需要预留空间，但不承诺所有算子都达到生产级性能。

不同规模下的处理策略应保持一致：Dataset、pack_artifact、逻辑算子结果和状态矩阵默认落盘；CleaningContext 只保存引用、摘要和运行状态。

#### 18.3 批处理与 staged 策略

CleaningContext 提供清洗流程默认 batch_config，例如：

```text
batch_size
write_batch_size
max_workers
in_flight_bytes
```

ExecutionPack 可以继承 CleaningContext 的 batch_config，也可以在 execution_config 中覆盖。

ExecutionPack 需要声明自己的执行能力：

1. batch_mode=enabled：支持按 batch 独立处理。
2. batch_mode=disabled：不支持按 batch 处理，需要全局计算。
3. batch_mode=staged：可以先分批生成中间结果，再进行全局阶段计算。

重复检测、离群检测和聚类这类全局能力通常不适合简单按 batch 独立完成，可以采用 staged 模式，例如先分批提取特征，再基于全量特征文件构建索引和输出重复组。

#### 18.4 Parquet 分片与扫描

raw Dataset、pack_artifact、node_result、node_status_matrix、merge_result 和导出数据集都应支持 Parquet 分片。

读取策略：

1. 优先使用列裁剪，只读取当前操作需要的字段。
2. 优先使用条件过滤，减少无关行读取。
3. 大规模读取时使用 scan 或 batch reader，不一次性读入内存。
4. 可视化和预览默认读取抽样或 limit 数据。

写入策略：

1. 按 write_batch_size 写出分片。
2. 分片写入完成后再提交正式产物。
3. Pack 或逻辑算子结果完成后记录分片数量、行数、输出路径和报告地址。

#### 18.5 图片读取与解码策略

图片读取和解码是性能瓶颈之一。清洗平台应优先通过 ExecutionPack 共享读取和解码结果，避免每个逻辑算子独立读取同一张图片。

默认策略：

1. 不一次性解码全部图片。
2. 只在当前 batch 内读取和解码图片。
3. 元数据抽取优先读取图片头信息，避免不必要的完整解码。
4. 可共享 decoded_image 的逻辑算子应优先融合到同一个 ImageDecodePack 或 OpenCVQualityPack。
5. 可视化只生成抽样缩略图。
6. 导出 HTML 报告时默认限制样本数量。
7. ExecutionPack 应优先通过受管本地缓存读取远程对象，降低重复读取 MinIO 的成本。

对于需要完整解码的质量检测、模糊检测、亮度检测等逻辑算子，应在同一个 ExecutionPack 级控制 batch_size、worker 数和 in-flight bytes，避免内存峰值过高。

#### 18.6 共享特征与 artifact 复用

以下中间产物应优先复用，不应由多个逻辑算子重复计算：

1. 图片基础元数据。
2. 图片 hash。
3. decoded_image 派生指标。
4. 质量指标。
5. pHash、aHash、dHash。
6. CLIP 或 fastdup embedding。
7. ANN index。
8. fastdup artifacts。
9. CleanVision issue summary。
10. Data-Juicer 中间输出。

artifact 复用必须校验 dataset_fingerprint、image_content_hash、operator_config_hash、backend_name、backend_version、code_version 和 artifact_schema_version。

#### 18.7 并行策略

第一版采用单机内受控并行：

```text
ExecutionPlan 可以包含依赖顺序
互不依赖的 ExecutionPack 后续可并行
ExecutionPack 内部优先支持 batch / worker 并行
ResultNormalizer 可以按逻辑算子或分片并行
```

第一版可以先实现串行 Pack 调度，但架构上不再把“逻辑算子顺序直跑”作为目标模型。即使 Pack 串行执行，也应保留 ExecutionPlan、operator_to_pack_mapping 和 artifact_reuse_plan。

节点内部并行应受 max_workers 控制，并需要考虑文件系统、MinIO、CPU、GPU 和第三方工具的实际承载能力。

#### 18.8 I/O 控制

文件系统和 MinIO 都可能受到大量小文件读写影响。

第一版需要控制：

1. 图片读取并发数。
2. Parquet 写入分片大小。
3. 缩略图生成数量。
4. MinIO 请求并发数。
5. 临时文件目录和正式产物目录的写入压力。
6. ExecutionPack 同时运行数量。
7. 单个 Pack 的 in-flight bytes。

存储后端差异应由 Storage Adapter 屏蔽，上层 Pack 不直接依赖文件系统或 MinIO SDK 细节。

#### 18.9 SQLite 性能边界

SQLite 只用于控制面状态存储，不进入图片级高频写入路径。

适合写入 SQLite 的内容：

1. run 状态。
2. operator 状态。
3. pack 状态。
4. batch 或 stage 状态。
5. artifact 索引。
6. 报告摘要。
7. 错误摘要。

不适合写入 SQLite 的内容：

1. 每张图片的元数据明细。
2. 每张图片的处理状态矩阵。
3. 大规模重复组明细。
4. 图片文件或缩略图二进制。
5. 高维 embedding 向量。

ExecutionPack 执行时可以按 batch 或 stage 更新 SQLite 状态，但不应对每张图片执行 SQLite 写入。

#### 18.10 可视化性能

可视化模块默认面向抽样查看，而不是全量浏览。

默认策略：

1. Notebook 表格预览默认限制 limit。
2. 图片网格预览默认限制图片数量。
3. 重复组预览默认限制 group 数量和每组图片数量。
4. HTML 报告默认导出样本和摘要，不导出全量图片预览。
5. 缩略图缓存索引可以写入 SQLite，缩略图文件本体写入文件系统或对象存储。

#### 18.11 扩展方向

后续如需要进一步提升性能，可以扩展：

1. 增强 ExecutionPlanner 的成本模型和依赖分析。
2. 支持互不依赖 ExecutionPack 的并行调度。
3. 引入 DuckDB 或 Polars LazyFrame 做更强的本地查询。
4. 引入分布式计算框架处理更大规模数据集。
5. 引入向量索引用于重复检测、相似图片检索和语义搜索。
6. 将 fastdup、CleanVision、CLIP、YOLO、NSFW 等重型后端拆成 extras 或插件包。

这些能力不属于第一版必须完整实现内容，但第一版数据契约应为其预留位置。

#### 18.12 设计原则

1. 第一版优先保证单机可用和可恢复。
2. 大规模数据默认落盘，不进入内存常驻。
3. 逻辑算子保持细粒度，物理执行包负责共享计算。
4. Parquet 是大规模表格产物的主要格式。
5. SQLite 只存轻量状态和索引。
6. 全局算子需要声明 staged 执行模式。
7. 可视化默认抽样，不做全量图片浏览。
