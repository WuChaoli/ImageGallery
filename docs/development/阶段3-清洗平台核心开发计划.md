# 阶段 3：清洗平台核心开发计划

本文档用于指导阶段 3 的开发顺序。阶段 3 只建立 v2 清洗平台的核心模型和最小 `BasicCleaner` 闭环，不追求完整算子覆盖，不引入 DAG、Planner、ExecutionPack 或每算子独立结果表。

## 1. 计划依据

1. `docs/development/图片数据集处理框架-顶层开发计划.md`
2. `docs/development/阶段1-公共基础能力开发计划.md`
3. `docs/development/阶段2-图片导入闭环开发计划.md`
4. `docs/architecture/modules/清洗平台与算子库-v2.md`
5. `docs/architecture/modules/清洗平台与算子库-v2-文件类函数设计.md`
6. `docs/architecture/modules/数据集管理与可视化.md`
7. `docs/architecture/modules/错误处理与恢复.md`

## 2. 开发目标

阶段 3 的目标是让 raw Dataset 能进入清洗平台，并形成最小可运行、可查看、可导出的清洗框架：

1. 提供 `BasicCleaner([{operator_name: config}, ...])` 用户入口。
2. 支持算子配置解析、默认配置合并和稳定配置 hash。
3. 提供 `OperatorSpec`、`OperatorRegistry` 和 `BackendAdapter` 协议。
4. 支持 `BasicCleaner` 按 `backend_name` 对算子请求分组运行。
5. 维护 `parameter_table`、`evaluation_table` 和 `operator_outputs` manifest。
6. 提供 `run`、`preview`、`state`、`result`、`config`、`rerun`、`export` 的最小 API 形态。
7. 使用 JSON manifest 记录第一版运行状态，SQLite 留到阶段 5。

## 3. 非目标

阶段 3 不做以下内容：

1. 不实现通用 DAG、Graph Runtime、ExecutionPlanner 或 ExecutionPack。
2. 不实现多个候选后端选择和全局执行优化。
3. 不为每个逻辑算子创建独立 `node_result` 或 `node_status_matrix` 表。
4. 不实现 fastdup、OpenCV、hash 等完整内置算子库。
5. 不实现 Notebook 图片网格、静态 HTML 报告或批量恢复。
6. 不把图片级明细写入 SQLite。
7. 不直接修改、删除或转换图片资产。
8. 不重新实现 Dataset、Storage 或 raw Dataset 读写能力。

## 6. 核心边界

### 6.1 Cleaner

`Cleaner` 是用户侧协议，固定清洗平台公开 API。

最小方法：

```text
run(dataset, output_dir=None, overwrite=False)
preview(limit=20)
state()
config(operator_configs)
rerun(operator_configs)
result(operator_name)
export(kind, path)
```

### 6.2 BasicCleaner

`BasicCleaner` 是第一版清洗策略，不是通用执行图。

负责：

1. 解析用户传入的 `list[{operator_name: config}]`。
2. 从 registry 解析 `OperatorSpec` 和唯一 `BackendAdapter`。
3. 按 `backend_name` 分组调用 `compute_parameters()`。
4. 调用每个 `OperatorSpec.evaluate()` 生成评估列。
5. 写出两张主表、manifest 和 JSON state。

不负责：

1. 跨后端依赖规划。
2. 多后端候选选择。
3. 图片资产删除或转换。
4. 大规模恢复和批处理状态机。

### 6.3 parameter_table

`parameter_table` 是图片级参数宽表。

最小基础列：

```text
image_id
image_uri
source_uri
```

阶段 3 只要求能接收 fake backend 写入的参数列，并能按 `image_id` 合并更新。

### 6.4 evaluation_table

`evaluation_table` 是图片级评估宽表。

最小基础列：

```text
image_id
image_uri
final_action
final_reason
triggered_operator_names
```

阶段 3 只要求能接收 `OperatorSpec.evaluate()` 写入的 action、reason、score 或 label 列，并能生成最终动作。

### 6.5 operator_outputs

`operator_outputs` manifest 记录每个逻辑算子的评估列。

用途：

1. `result(operator_name)` 定位算子结果列。
2. `config()` 和 `rerun()` 定位需要失效或覆盖的列。
3. `preview()` 识别参与最终动作归并的 action/reason 列。

## 7. 开发顺序

### 步骤 1：配置解析与错误类型

实现：

1. `cleaning/errors.py`
2. `cleaning/config.py`

验证：

1. 非空 `list[{operator_name: config}]` 可以解析。
2. 单项包含多个 operator 会被拒绝。
3. 空 operator name 会被拒绝。
4. 非 dict config 会被拒绝。
5. 重复 operator name 会被拒绝。
6. hash 对同一配置稳定，对不同配置不同。

### 步骤 2：算子规格、注册表和后端协议

实现：

1. `operators/spec.py`
2. `operators/registry.py`
3. `operators/backends/base.py`

验证：

1. 可以注册并查询 `OperatorSpec`。
2. 可以注册并查询 `BackendAdapter`。
3. 未知 operator 和未知 backend 会返回明确错误。
4. `OperatorSpec.evaluate()` 校验输出包含 `image_id` 和声明的 evaluation columns。
5. backend 结果必须包含可按 `image_id` 合并的参数更新。

### 步骤 3：运行上下文和产物路径

实现：

1. `cleaning/context.py`

验证：

1. 可以根据 Dataset、cleaner_type 和 output_dir 创建 run context。
2. 可以生成 `parameter_table.parquet`、`evaluation_table.parquet`、`operator_outputs.yaml`、`relations/`、`artifacts/`、`state.json` 路径。
3. `run_id` 在同一进程内不重复。
4. 默认输出路径不污染源码目录。

### 步骤 4：宽表初始化与更新

实现：

1. `cleaning/tables.py`

验证：

1. raw Dataset 包含 `image_id` 和 `image_uri` 时可以初始化参数表。
2. 缺少 `image_id` 或 `image_uri` 会明确失败。
3. 参数列可以按 `image_id` 合并进 `parameter_table`。
4. 评估列只覆盖当前算子声明的输出列。
5. 不允许一个算子覆盖另一个算子已经占用的输出列。
6. 表和 `operator_outputs` 可以写入并重新读取。

### 步骤 5：preview 和 final_action

实现：

1. `cleaning/preview.py`

验证：

1. action 优先级为 `restricted > drop > review > keep`。
2. 没有命中任何 action 的图片默认 `keep`。
3. 可以生成 clean、review、dropped、restricted 数量。
4. `triggered_operator_names` 能记录触发最终动作的算子名。
5. preview 不修改 raw Dataset。

### 步骤 6：export 最小视图

实现：

1. `cleaning/export.py`

验证：

1. `parameters` 导出 `parameter_table`。
2. `evaluations` 导出 `evaluation_table`。
3. `full` 导出全部评估行。
4. `clean` 导出 `final_action == "keep"`。
5. `review` 导出 `final_action == "review"`。
6. `dropped` 导出 `final_action == "drop"`。
7. `restricted` 第一版不混入 dropped。

### 步骤 7：JSON 运行状态

实现：

1. `cleaning/state.py`

验证：

1. 可以保存和读取 `CleanerRunState`。
2. `state()` 可以返回算子级状态矩阵。
3. 状态记录 run_id、dataset_fingerprint、cleaner_type、配置 hash、输出路径和算子摘要。
4. JSON state 使用原子写入。

### 步骤 8：BasicCleaner 最小闭环

实现：

1. `cleaning/cleaner.py`
2. `cleaning/basic.py`
3. `cleaning/__init__.py`
4. `operators/__init__.py`

验证：

1. fake backend 可以被多个 fake operator 共享。
2. `run()` 会按 backend 分组，而不是每个 operator 单独调用 backend。
3. backend 只写 `parameter_table`，不写 `evaluation_table`。
4. evaluator 只读 `parameter_table` 并生成声明的评估列。
5. `preview()`、`state()`、`result()`、`export()` 在 run 后可用。
6. run 前调用依赖运行结果的方法会明确失败。

### 步骤 9：config 和 rerun 框架

实现：

1. `BasicCleaner.config()`
2. `BasicCleaner.rerun()`

验证：

1. `config()` 只更新配置和 stale 状态，不主动重算参数。
2. `rerun()` 要求已经执行过 `run()`。
3. `rerun()` 只重新执行传入算子所在的 backend group。
4. 重新评估后 final_action 会同步更新。
5. 状态文件记录新配置 hash 和算子运行状态。

## 8. 验收标准

阶段 3 完成时应满足：

1. `BasicCleaner` 可以接收 `list[{operator_name: config}]`。
2. 可以从 raw Dataset 初始化 `parameter_table` 和 `evaluation_table`。
3. 可以通过 registry 把逻辑算子绑定到唯一 backend。
4. 可以按 backend 分组执行参数计算。
5. 可以通过 evaluator 生成逻辑算子评估列。
6. 可以生成 `operator_outputs` manifest。
7. 可以生成 `preview()`、`state()`、`result()` 和 `export()` 的最小结果。
8. 可以保存 JSON state。
9. 单元测试覆盖配置、registry、backend contract、表更新、preview、state 和 BasicCleaner。
10. 不包含 DAG、Planner、ExecutionPack、node_result、node_status_matrix 或 SQLite 恢复实现。

## 9. 后续衔接

1. Pillow metadata backend 和 format/size 算子。

5. full、clean、review、dropped、parameters、evaluations 的真实样本导出验证。
