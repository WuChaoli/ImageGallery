# 阶段 4：第一批算子与结果归并开发计划

本文档用于指导阶段 4 的开发顺序。阶段 4 在阶段 3 的清洗平台核心之上，实现第一批内置逻辑算子、真实后端 adapter、最终动作归并和导出视图验证。

1. `docs/development/图片数据集处理框架-顶层开发计划.md`
2. `docs/development/阶段3-清洗平台核心开发计划.md`
3. `docs/architecture/modules/清洗平台与算子库-v2.md`
4. `docs/architecture/modules/清洗平台与算子库-v2-文件类函数设计.md`

## 2. 开发目标

阶段 4 的目标是跑通第一条真实清洗链路：

1. 实现第一批能力优先命名的内置算子。
2. 实现 Pillow、OpenCV 和 image hash 后端。
3. 为 fastdup 后端保留明确接口；依赖不可用时返回明确错误，不阻塞基础链路。
4. 验证同一 backend 下多个逻辑算子只触发一次 backend 调用。
5. 验证后端输出进入 `parameter_table`，逻辑算子输出进入 `evaluation_table`。
6. 验证 `final_action` 归并和 `clean`、`review`、`dropped`、`full` 导出。

## 3. 非目标

阶段 4 不做以下内容：

1. 不引入 DAG、Planner、ExecutionPack。
2. 不实现生产级 fastdup 调优、ANN index 管理或跨 run 缓存。
3. 不实现 CleanVision、NSFW、OCR、caption、语义重复等重型能力。
4. 不实现 Notebook 图片网格或静态 HTML 报告。
5. 不实现 SQLite Run State Store、resume、retry_failed 或批级恢复。
6. 不在检测类算子中删除、移动或修改图片资产。
7. 不把 relation/artifact 的恢复语义提前做成平台控制面。

## 6. 第一批算子范围

阶段 4 优先实现不依赖重型外部服务的算子：

```text
format.decode_check
size.dimension_check
quality.blur_check
quality.brightness_check
quality.contrast_check
duplicate.exact_duplicate_check
```

阶段 4 预留或条件实现：

```text
duplicate.near_duplicate_check
distribution.outlier_check
distribution.cluster_check
```

如果 fastdup 依赖暂不可用，相关算子可以注册但运行时抛出明确依赖错误，或暂不进入默认 quickstart。无论选择哪种方式，都要保证基础算子链路可验收。

## 7. 后端与算子映射

```text
format.decode_check
  -> pillow_metadata_backend

size.dimension_check
  -> pillow_metadata_backend

quality.blur_check
  -> opencv_quality_backend

quality.brightness_check
  -> opencv_quality_backend

quality.contrast_check
  -> opencv_quality_backend

duplicate.exact_duplicate_check
  -> image_hash_backend

duplicate.near_duplicate_check
  -> fastdup_similarity_backend
```

核心约束：

1. 用户面对的是逻辑算子名，不是后端工具名。
2. 每个逻辑算子当前只绑定一个明确后端。
3. backend 只写参数、关系和 artifact 引用，不写平台 action。
4. evaluator 只根据参数表和配置生成评估列。
5. 同一后端的多个逻辑算子必须能合并为一次 adapter 调用。

## 8. 开发顺序

### 步骤 1：内置 registry 与 evaluator 骨架

实现：

1. `operators/builtin.py`
2. 默认 `create_default_registry()`
3. 内置 evaluator 函数

验证：

1. 默认 registry 包含阶段 4 范围内的算子。
2. 每个算子包含 name、category、backend_name、parameter_columns、evaluation_columns、default_config、action_column、reason_column。
3. evaluator 输出包含 `image_id` 和声明的 evaluation columns。
4. evaluator 不读取图片、不调用后端、不修改输入参数表。

### 步骤 2：Pillow metadata backend

实现：

1. `operators/backends/pillow_backend.py`
2. `format.decode_check`
3. `size.dimension_check`

参数列：

```text
width
height
format
decode_ok
decode_error
```

评估列：

```text
decode_action
decode_reason
dimension_action
dimension_reason
```

验证：

1. 正常图片能写入宽高、格式和 decode 状态。
2. 损坏图片不会中断整批运行，而是写入 decode error。
3. 尺寸阈值变化只需要重算 evaluation columns。
4. `format.decode_check` 和 `size.dimension_check` 共享一次 pillow backend 调用。

### 步骤 3：OpenCV quality backend

实现：

1. `operators/backends/opencv_backend.py`
2. `quality.blur_check`
3. `quality.brightness_check`
4. `quality.contrast_check`

参数列：

```text
blur_score
brightness_score
contrast_score
```

评估列：

```text
blur_score
blur_action
blur_reason
brightness_score
brightness_action
brightness_reason
contrast_score
contrast_action
contrast_reason
```

验证：

1. 可以对小样本图片计算 blur、brightness、contrast 参数。
2. 三个质量算子共享一次 opencv backend 调用。
3. 阈值调整可以改变 evaluation_table，不需要改写 raw Dataset。
4. 后端依赖缺失时错误信息明确指向可安装依赖。

### 步骤 4：Image hash backend

实现：

1. `operators/backends/hash_backend.py`
2. `duplicate.exact_duplicate_check`

参数列：

```text
content_hash
phash
exact_duplicate_group_id
```

评估列：

```text
exact_duplicate_group_id
exact_duplicate_action
exact_duplicate_reason
```

验证：

1. 相同文件内容可以得到相同 content hash。
2. 完全重复图片可以分到同一 duplicate group。
3. 非重复图片不会被错误标记为 duplicate。
4. `exact_duplicate_action` 默认可配置为 `drop` 或 `review`。

### 步骤 5：fastdup backend 边界

实现或占位：

1. `operators/backends/fastdup_backend.py`
2. `duplicate.near_duplicate_check`
3. 可选 `distribution.outlier_check`
4. 可选 `distribution.cluster_check`

最小要求：

1. 如果 fastdup 不可用，错误信息明确说明安装方式和受影响算子。
2. 如果 fastdup 可用，可以把原始输出归一化为参数列、relation table 和 artifact 引用。
3. 同一次 fastdup backend 调用可以服务近重复、离群和聚类请求。

验证：

1. 无 fastdup 环境下，基础算子测试不失败。
2. fastdup 相关测试可通过 skip marker 或 extras 条件控制。
3. 上层 `BasicCleaner` 不感知 fastdup SDK 细节。

### 步骤 6：最终动作归并策略验证

实现或补强：

1. `apply_final_action()`
2. `build_preview()`
3. operator action/reason 聚合规则

验证：

1. 优先级保持 `restricted > drop > review > keep`。
2. 多个算子同时命中时，`final_reason` 能聚合关键原因。
3. `triggered_operator_names` 能记录命中的逻辑算子。
4. 单个算子的 result 只返回该算子拥有的列。
5. 物理 backend 分组不影响逻辑算子级查看。

### 步骤 7：导出视图

实现或补强：

1. `export(kind="full")`
2. `export(kind="clean")`
3. `export(kind="review")`
4. `export(kind="dropped")`
5. `export(kind="parameters")`
6. `export(kind="evaluations")`

验证：

1. `full` 包含全部图片。
2. `clean` 只包含 `final_action == "keep"`。
3. `review` 只包含 `final_action == "review"`。
4. `dropped` 只包含 `final_action == "drop"`。
5. `restricted` 第一版不混入 dropped。
6. `clean + review + dropped + restricted = full` 可以通过计数验证。
7. 导出的 Dataset 可以被阶段 1 Dataset 模块重新读取。

### 步骤 8：rerun 行为验证

实现或补强：

1. 评估参数变化的局部重算。
2. 运算参数变化的参数重算和评估级联更新。

验证：

1. 调整 blur threshold 后，只需更新 blur 评估列和 final_action。
2. 调整 hash 或 fastdup 运行参数时，会重新执行对应 backend。
3. 其他不相关算子的输出列不被覆盖。
4. state 记录最新配置 hash 和算子状态。

### 步骤 9：示例与集成验收

实现：

2. 小样本集成测试

验证：

.venv/bin/python examples/stage4_basic_cleaner_quickstart.py

4. 输出 preview 统计。

## 9. 验收标准

阶段 4 完成时应满足：

1. 默认 registry 至少包含 format、size、quality 和 exact duplicate 算子。
2. Pillow backend 可以支撑 decode 和 dimension 算子。
3. OpenCV backend 可以支撑 blur、brightness 和 contrast 算子。
4. Image hash backend 可以支撑 exact duplicate 算子。
5. fastdup backend 有明确边界，依赖不可用时不会阻塞基础链路。
6. 至少两个共享 backend 的逻辑算子可以合并为一次 backend 调用。
7. 每个逻辑算子都可以通过 `result(operator_name)` 查看独立评估结果。
8. `preview()` 能展示 clean、review、dropped、restricted 统计。
9. `export()` 能导出 full、clean、review、dropped、parameters、evaluations。
10. `clean + review + dropped + restricted = full` 被集成测试验证。
11. 不包含 DAG、Planner、ExecutionPack、SQLite 恢复或 Notebook 报告实现。
