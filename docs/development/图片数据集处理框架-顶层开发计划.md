# 图片数据集处理框架顶层开发计划

本文档用于指导第一版开发顺序，只定义阶段、依赖、交付边界和顶层验收口径。模块内的对象设计、接口设计、字段设计、测试用例和实现细节，放到对应模块开发计划中展开。

## 1. 计划依据

本计划依据以下文档整理：

1. `docs/prds/图片数据集处理框架-PRD.md`
2. `docs/architecture/图片数据集处理框架-总体架构.md`
3. `docs/architecture/modules/图片导入与元数据.md`
4. `docs/architecture/modules/存储系统.md`
5. `docs/architecture/modules/数据集管理与可视化.md`
6. `docs/architecture/modules/清洗平台与算子库.md`
7. `docs/architecture/modules/错误处理与恢复.md`
8. `docs/architecture/modules/性能与扩展.md`

## 2. 第一版目标

第一版目标是完成 Python package 和 Jupyter 调试形态下的本地数据处理闭环：

```text
外部图片来源
  -> 图片导入
  -> 平台统一存储
  -> raw Dataset
  -> BasicCleaner
  -> parameter_table / evaluation_table
  -> full / clean / dropped Dataset
  -> DatasetViewer / report / export
```

第一版不实现服务端 API、Web 页面、多用户权限、图片增强、跨机器分布式 DAG 调度和完整数据集版本管理。

## 3. 开发原则

1. 先公共能力，后业务流程。
2. 先形成 raw Dataset，再进入清洗平台。
3. 先保证逻辑算子结果可追踪，再做 clean、dropped、full 归并。
4. 先完成小样本端到端闭环，再做十万级规模验证。
5. 先交付 Python 包公开 API 和 Notebook 验收流程，后续平台化只包装已有能力。

## 4. 阶段路线图

### 阶段 0：项目骨架与工程基线

目标：建立可持续开发的最小工程环境。

主要范围：

1. 建立 `src/image_gallery/` 包结构。
2. 建立 `tests/`、`examples/`、`notebooks/` 基础目录。
3. 建立基础配置、测试、格式化和本地运行约定。
4. 固化第一批公开 API 的命名边界，不提前实现模块内部复杂逻辑。

依赖：无。

完成标准：

1. Python 包可以被本地安装和导入。
2. 最小测试命令可以运行。
3. 示例和 Notebook 目录有明确占位入口。

后续模块计划：

1. `docs/development/阶段0-项目骨架与工程基线开发计划.md`

### 阶段 1：公共基础能力

目标：先建立后续导入、清洗、查看都要复用的最小底座，不提前实现清洗平台控制面。

主要范围：

1. Storage：文件系统存储、MinIO 接入、image_uri 生成、受管输出路径。
2. Dataset：Parquet 读写、预览、扫描、导出和 fingerprint。
3. Raw Schema：只定义导入阶段生成 raw Dataset 所需的最小字段契约。
4. 公共约定：为后续清洗产物、运行状态和产物索引预留目录与命名边界，但不实现清洗语义。

依赖：阶段 0。

完成标准：

1. 可以把数据写入受管 storage，并通过 `image_uri` 重新读取。
2. 可以写出和读取 Parquet Dataset。
3. 可以校验 raw Dataset 的最小字段契约。
4. 不包含 BasicCleaner、OperatorRegistry、parameter_table、evaluation_table、preview/export 或清洗恢复逻辑。

后续模块计划：

1. `docs/development/阶段1-公共基础能力开发计划.md`
2. `docs/development/阶段1-Storage开发计划.md`
3. 数据集管理开发计划。
4. raw Dataset 字段契约开发计划。

### 阶段 2：图片导入闭环

目标：把外部图片来源稳定转换为平台内 raw Dataset。

主要范围：

1. 本地目录导入。
2. 已有数据集文件导入。
3. 基础 URL 清单导入。
4. 图片复制或登记到平台统一存储。
5. 基础图片元数据抽取。
6. raw Dataset、import_report 和 failure_manifest 输出。

依赖：阶段 1。

完成标准：

1. 可以从本地目录导入图片并生成 raw Dataset。
2. raw Dataset 使用 `image_uri` 作为后续处理主引用。
3. 单张图片失败不阻断整批导入，并能写入失败清单。
4. Notebook 或 example 可以展示导入结果。

后续模块计划：

1. `docs/development/阶段2-图片导入闭环开发计划.md`
2. 图片导入与元数据开发计划。

### 阶段 3：清洗核心模型

目标：建立 v2 清洗平台的核心模型和最小 `BasicCleaner` 闭环，但先不追求完整算子覆盖。

主要范围：

1. Cleaner / BasicCleaner 用户入口。
2. OperatorSpec 和 OperatorRegistry。
3. BackendAdapter 协议和 backend 分组运行机制。
4. CleanerRunContext 和 JSON CleanerRunState。
5. parameter_table、evaluation_table 和 operator_outputs manifest。
6. preview、state、result、config、rerun、export 的最小 API 闭环。

依赖：阶段 1、阶段 2。

完成标准：

1. 可以加载 raw Dataset 并创建 BasicCleaner。
2. 可以解析 `list[{operator_name: config}]` 并绑定唯一 OperatorSpec 与 BackendAdapter。
3. 可以初始化并写出 parameter_table、evaluation_table 和 operator_outputs manifest。
4. 至少一个轻量内置算子能完成参数计算、评估列生成、preview/state/result/export。

后续模块计划：

1. `docs/development/阶段3-清洗平台核心开发计划.md`

### 阶段 4：第一批算子与结果归并

目标：完成第一条可验证的清洗链路。

主要范围：

1. 格式类基础算子。
2. 尺寸类基础算子。
3. 质量类基础算子。
4. BasicCleaner 内部按 backend 分组运行，避免重复读取、重复解码或重复 fastdup 执行。
5. final_action 归并、preview 和 export。
6. full、clean、dropped、review、parameters、evaluations Dataset 输出。

依赖：阶段 3。

完成标准：

1. 至少两个共享读取、解码或质量指标的逻辑算子可以合并到同一个 backend adapter 调用。
2. 物理融合不改变逻辑算子级结果查看和错误解释。
3. 可以生成 full、clean、dropped、review、parameters、evaluations。
4. `clean + review + dropped + restricted = full` 可以被测试验证，其中 restricted 第一版不混入 dropped。

后续模块计划：

1. `docs/development/阶段4-第一批算子与结果归并开发计划.md`

### 阶段 5：查看、报告与恢复

目标：让处理结果可检查、可分享、可恢复。

主要范围：

1. DatasetViewer。
2. Notebook 图片网格和表格查看。
3. dropped 候选、异常样本和重复组查看。
4. 静态 HTML 报告。
5. SQLite Run State Store。
6. artifact manifest、原子提交和产物索引。
7. batch 级断点恢复。
8. overwrite、resume、retry_failed、rerun_operator、rerun_backend_group 的顶层语义。

依赖：阶段 4。

完成标准：

1. 可以在 Notebook 查看 raw、full、clean、dropped。
2. 可以查看丢弃原因、算子结果分布和失败摘要。
3. 可以导出静态 HTML 报告。
4. 中断后可以基于 SQLite 状态和 artifact manifest 恢复运行。

后续模块计划：

1. 数据集可视化与报告开发计划。
2. 错误处理与恢复开发计划。

### 阶段 6：验收固化与规模验证

目标：把第一版能力固化为可交付、可演示、可回归的版本。

主要范围：

1. 小样本端到端集成测试。
2. 十万级数据规模边界验证。
3. 公开 API 示例。
4. Notebook 验收流程。
5. 文档和模块开发计划回填。
6. 性能瓶颈、非目标和后续演进记录。

依赖：阶段 5。

完成标准：

1. 从导入到清洗、归并、查看、导出的本地闭环可以完整跑通。
2. 核心公开 API 有示例覆盖。
3. 十万级验证结果有记录，包括耗时、失败情况、资源占用和已知限制。
4. 第一版非目标不会被误认为已交付能力。

后续模块计划：

1. 端到端验收开发计划。
2. 性能与规模验证计划。

## 5. 顶层依赖关系

```text
阶段 0：项目骨架与工程基线
  -> 阶段 1：公共基础能力
    -> 阶段 2：图片导入闭环
      -> 阶段 3：清洗核心模型
        -> 阶段 4：第一批算子与结果归并
          -> 阶段 5：查看、报告与恢复
            -> 阶段 6：验收固化与规模验证
```

其中，状态、报告、错误恢复和性能策略不应等到最后才补齐。它们在阶段 1 建立最小底座，在阶段 3 到阶段 5 随清洗流程逐步补全。

## 7. 顶层验收口径

第一版最终验收只看本地闭环是否成立：

1. 能从本地目录导入图片，写入统一存储，并生成 raw Dataset。
2. 能读取、预览、扫描、导出和 fingerprint Dataset。
3. 能配置 BasicCleaner 和能力优先的逻辑算子列表。
4. 能按 backend 分组执行至少两个共享后端的逻辑算子。
5. 能为每个逻辑算子生成 parameter_table 字段、evaluation_table 字段和 operator_outputs 记录。
6. 能导出 full、clean、review、dropped，且 `clean + review + dropped + restricted = full`。
7. 能查看丢弃原因、异常样本、重复组或 dropped 候选。
8. 能记录失败清单、错误摘要、运行状态和 artifact manifest。
9. 能在中断后基于 SQLite 状态和 artifact manifest 恢复运行。
10. 不依赖服务端 API 和 Web 页面即可完成核心流程。

## 8. 暂不进入本计划的内容

以下内容不进入第一版顶层开发计划：

1. FastAPI 服务。
2. Web 前端。
3. 多用户权限。
4. PostgreSQL。
5. 图片增强。
6. 标注协同。
7. 完整数据集版本管理。
8. 跨机器分布式 DAG 调度。
9. 外部向量检索服务。
10. 生产级 NSFW、隐私识别和语义重复模型。
